# Questionnaire Section Architecture Review

> سجل القرارات المعمارية الخاصة بإعادة تنظيم أقسام الاستبيان قبل دورة الإجابات الجديدة.
>
> هذا الملف يشرح **لماذا** تم تقسيم الأقسام بهذه الطريقة وما الذي نُقل أو دمج أو أُلغي كقسم مستقل. لا يستخدم كـImplementation Checklist؛ متابعة التنفيذ موجودة في:
>
> `docs/QUESTIONNAIRE_ARCHITECTURE_IMPLEMENTATION_PLAN.md`
>
> المرجع الأعلى للحالة الحالية:
>
> `docs/FARM_BLUEPRINT_PROJECT_CONTEXT.md`

---

## 1. سبب المراجعة

خلال مرحلة التطوير الحالية يعتمد المشروع محليًا على:

```bash
php artisan migrate:refresh --seed
```

وبما أن الإجابات القديمة تم الاستغناء عنها قبل بدء دورة إجابات مستقرة، تم استغلال هذه المرحلة لإعادة تنظيم الأقسام قبل تثبيت إجابات نريد الحفاظ عليها لاحقًا.

الأهداف:

1. جعل مسؤولية كل Main Section واضحة.
2. منع تكرار نفس القرار بين Data / Workflow / Reports / Settings.
3. نقل الموضوع الموجود في المكان الخطأ.
4. اكتشاف النطاقات المفقودة قبل بناء الأسئلة.
5. جعل Question Seeder tree لاحقًا مطابقًا للشجرة الوظيفية.
6. توثيق سبب كل قرار حتى لا نعتمد على الذاكرة أو المحادثة.

---

## 2. حالات القرارات

- **APPROVED** — قرار معتمد ويمكن البناء عليه.
- **PROPOSED** — اقتراح لم يعتمد بعد.
- **TO REVIEW** — موضوع يحتاج مراجعة مخصصة.
- **MOVED** — موضوع نقل إلى قسم آخر.
- **REMOVED** — ألغي كقسم مستقل مع الحفاظ على مضمونه في المكان الصحيح.

لا يعتبر `PROPOSED` أو `TO REVIEW` Requirement نهائيًا.

---

## 3. قاعدة الفصل المعماري — APPROVED

```text
What IS it?
→ Master Data / Farm Structure / Animal Data

What HAPPENED?
→ Workflow

What do we KNOW from what happened?
→ Reports / Analytics

What RULES control what should happen?
→ Settings
```

بصياغة عربية:

```text
ما هو الشيء أو الكيان؟ → البيانات
ما الذي حدث فعليًا؟ → الحركات
ماذا نعرض أو نستنتج؟ → التقارير والتحليلات
ما القواعد التي تتحكم فيما يجب أن يحدث؟ → الإعدادات
```

هذه القاعدة مرجع إلزامي أثناء إنشاء الأسئلة.

---

## 4. الهيكل الرئيسي المعتمد — APPROVED

```text
1. إدارة البيانات الأساسية
2. هيكل المزرعة
3. بيانات الحيوان وتكوين القطيع
4. الحركات ودورة التشغيل الفعلية
5. التقارير والتحليلات والتنبيهات ومؤشرات الأداء
6. الإعدادات وقواعد التشغيل
```

### لماذا Settings هو آخر Main Section؟

ترتيب الدراسة المعتمد:

```text
الكيانات والبيانات
→ الحركات الفعلية
→ التقارير والمخرجات المطلوبة
→ القواعد والإعدادات التي تتحكم فيما سبق
```

الهدف أن نفهم أولًا ماذا يوجد، وما الذي يحدث، وما الذي نريد عرضه أو قياسه، ثم نحدد ما الذي يجب أن يكون قابلًا للتخصيص.

# القسم الثالث — بيانات الحيوان وتكوين القطيع

## 5. الشجرة المعتمدة — APPROVED

```text
3. بيانات الحيوان وتكوين القطيع
├── 3.1 بيانات وهوية الحيوان
├── 3.2 مصدر الحيوان وبداية السجل
├── 3.3 النسب وشجرة العائلة
├── 3.4 القطيع الافتتاحي وتهيئة نقطة البداية
└── 3.5 تكوين القطيع الإنتاجي وتنظيم المجموعات
```

### 5.1 بيانات وهوية الحيوان

Animal Record يستمر مع نفس الحيوان طوال حياته.

لا تعامل القيم المشتقة من الأحداث كحقول ثابتة تعدل يدويًا، مثل:

- الموقع الحالي.
- الوزن الحالي.
- الجاهزية الحالية.
- الحالة الإنتاجية الحالية.

### 5.2 مصدر الحيوان وبداية السجل

يجيب عن:

> من أين بدأت معرفة النظام بهذا الحيوان وما أول نقطة موثقة في سجله؟

المبدأ:

> لا يتم اختراع تاريخ غير معروف؛ يبدأ النظام من أول معلومة موثوقة متاحة.

### 5.3 النسب وشجرة العائلة

```text
Breed
= تعريف السلالة المرجعي في Master Data

Animal Pedigree
= الأب + الأم + علاقات القرابة + شجرة العائلة الفعلية للحيوان
```

### 5.4 القطيع الافتتاحي

يعالج بدء النظام في مزرعة قائمة بالفعل وبها حيوانات في مراحل مختلفة، مثل حامل أو مرضعة أو نمو أو تسمين أو حالات صحية، دون اختلاق تاريخ سابق.

### 5.5 تكوين القطيع الإنتاجي وتنظيم المجموعات

```text
مفهوم Production Group وتكوينه → Animal/Herd Data
النسب المستهدفة وقواعد الجاهزية → Settings
تغيير عضو أو اعتماد/إخراج أثناء التشغيل → Workflow
```

## 6. ما تم نقله من القسم القديم — APPROVED

### MOVED → Workflow

- `الدخول الأول للمزرعة والتقييم الأولي`.
- `تسكين القطيع وإدارة الإشغال`.
- `تحويل إنتاج المزرعة إلى القطيع والإحلال الداخلي` كتنفيذ فعلي.

### REMOVED ككتلة واحدة: جاهزية القطيع

```text
قواعد الجاهزية → Settings
التحول أو القرار الفعلي → Workflow
عرض الجاهزية وأسباب عدمها → Reports / Dashboard
```

# القسم الرابع — الحركات ودورة التشغيل الفعلية

## 7. تعريف Workflow — APPROVED

Workflow مسؤول عن:

> **كل حدث أو إجراء فعلي يحدث بمرور الوقت ويغير سجل الحيوان أو البطن أو دورة الإنتاج أو موقع الإيواء أو المهمة التشغيلية.**

```text
Entity / Data = من هو الحيوان؟ وما هو القفص؟
Workflow = ماذا حدث؟ ومتى؟ ولماذا؟ ومن نفذه؟
```

## 9. قرارات إعادة التنظيم — APPROVED

- بدء دورة الأنثى + تكرار التلقيح → `التلقيح وإدارة المحاولات`.
- الجس + متابعة الحمل وتجهيز الولادة → مسار حمل واحد.
- إعادة تلقيح الأم أثناء الرضاعة → جزء من `تداخل دورات الأم` وليس Subsection مستقلًا.
- الفطام يبقى Boundary بين Litter Tracking وIndividual Tracking.
- قرار المصير القديم تفكك إلى تحديد مصير + إحلال + تسمين.
- الخروج يتطور ليشمل إعادة الدخول مع الحفاظ على الهوية.
- أعمال المواقع والمهام تبقى داخل Workflow بدل إنشاء Main Sections مستقلة.

### الوزن

## 13. قرارات الدمج والنقل — APPROVED

- `المهام والتنبيهات اليومية` → العرض في Dashboard/Alerts، التنفيذ في Workflow.
- `تقارير القطيع` توسعت لتشمل الجاهزية.
- `تقارير الخصوبة والتلقيح` توسعت لتشمل الحمل.
- `تقارير النفوق والصحة` توسعت لتشمل العزل.
- تقييم الإناث والذكور → `تحليل أداء الحيوانات الإنتاجية`.
- المقارنات الزمنية والمكانية → نطاق واحد.
- صفحة الحيوان + صفحة البطن → `الصفحات والسجلات التحليلية`.
- سجل التنبيهات → داخل التنبيهات والإنذار المبكر مع الحفاظ على التاريخ.
- `مستويات التنبيه` → MOVED إلى Settings.
- التصفية والتصدير → Cross-cutting Reporting Capability.
- `التقرير → التنبيه → القرار → الإجراء` → مبدأ معماري وليس Subsection.

```text
↓

↓

↓
```


```text

```

# القسم السادس — الإعدادات وقواعد التشغيل

## 14. منهج بناء Settings — APPROVED

يجب مراجعة الأقسام **1–5 كلها** لاستخراج القواعد المحتمل جعلها قابلة للتخصيص، بما في ذلك Master Data وFarm Structure.

لكن:

```text
Structural / System Rule ≠ Operational Setting
```

```text
Structural / System Rule
= قاعدة ثابتة ناتجة من تصميم الـBlueprint أو تعريف الكيان

Operational Setting
= قاعدة تشغيل يراد أن تكون قابلة للضبط أو الاختلاف حسب Scope

Runtime Event / Decision
= ما حدث فعليًا نتيجة تطبيق القواعد
```

لا يتحول القسم السادس إلى مكان يجمع كل Business Rule.

## 15. الشجرة النهائية — APPROVED

```text
6. الإعدادات وقواعد التشغيل
├── 6.1 نموذج الإعدادات ونطاق التطبيق
├── 6.2 السياسات العامة والتحكم والتجاوز والتدقيق
├── 6.3 قواعد تشغيل هيكل المزرعة ومواقع الإيواء
├── 6.4 قواعد التسكين وتنظيم القطيع والجاهزية
├── 6.5 قواعد التلقيح والخصوبة والجاهزية التناسلية
├── 6.6 قواعد فحص الحمل والحمل وتجهيز الولادة
├── 6.7 قواعد الولادة والرضاعة وإعادة التلقيح
├── 6.8 قواعد الفطام والانتقال للتتبع الفردي
├── 6.9 قواعد النمو والوزن والفرز والإحلال
├── 6.10 قواعد التسمين والجاهزية للبيع
├── 6.11 قواعد الصحة والعزل والنفوق والحالات الاستثنائية
├── 6.12 قواعد المهام والتنبيهات والمواعيد والأولويات
```

`الخروج` لا يوجد في اسم 6.10 لأن الجاهزية للبيع Setting/Derived Readiness بينما البيع والخروج الفعلي Workflow Event.

## 16. 6.1 نموذج الإعدادات ونطاق التطبيق — APPROVED

وظيفته تعريف Architecture منظومة Settings نفسها.

المبادئ:

```text
Structural / System Rule ≠ Operational Setting
Operational Settings may have a Scope
Settings changes must be historically explainable
```

الموضوعات التالية **أسئلة وليست افتراضات**:

- System / Farm / Barn / Profile Scope.
- العلاقة بين Farm / Barn / Operational Settings Profile.
- Reusable Profiles.
- Defaults / Inheritance.
- Overrides.
- أكثر من Profile فعال.
- Effective Date.
- Versioning.
- أثر تعديل Settings على العمليات الجارية والمهام القائمة.
- Historical Settings Reference / Snapshot.
- صلاحيات واعتماد التغييرات.

المبدأ التاريخي:

> تغيير الإعدادات لا يجوز أن يجعل الماضي يفسر باستخدام قيمة حالية مختلفة عن السياق الذي حدث فيه.

---

## 17. 6.2 السياسات العامة والتحكم والتجاوز والتدقيق — APPROVED

لا يعيد تعريف:

- Code Identity.
- Unique Scope.
- Entity Statuses.
- Relationships.
- Delete / Retirement Policy.
- Fixed/Managed Master Data Lists.

هذه تبقى مع Entity أو Master Data.

6.2 يراجع:

```text
Information
Warning
Block
```

مع إمكانية وجود Hard Constraints لا تسمح Override.

كما يراجع:

- Override Policy.
- Action Permission ≠ Override Permission.
- سبب وApproval التجاوز عند الحاجة.
- Sensitive Record Correction.
- Minimum Audit Trail.
- الجزء القابل للتهيئة من Code Generation فقط عند الحاجة.

---

## 18. 6.3 قواعد تشغيل هيكل المزرعة ومواقع الإيواء — APPROVED

يغطي القواعد القابلة للتخصيص مثل:

- الإتاحة التشغيلية.
- السعة التشغيلية.
- التفعيل عندما يكون Setting فعلًا.
- أثر الصيانة على الإتاحة.
- إلزام التطهير.
- فترة الانتظار.
- شروط إعادة الاستخدام.
- تغيير الاستخدام التشغيلي للموقع.

ولا يعيد تعريف Farm/Barn/Battery/Cage أو حالاتها أو Unique Codes.

ولا يفترض Environmental Control Module أو Setpoints لمجرد وجود أنظمة تهوية/تبريد/تدفئة كMaster Data.

---

## 19. 6.4 قواعد التسكين وتنظيم القطيع والجاهزية — APPROVED

يغطي:

- أهلية القفص أو الموقع لاستقبال الحيوان.
- توافق الاستخدام مع المرحلة.
- الجمع والسعة.
- الفصل حسب الجنس.
- تنظيم Production Groups.
- النسب المستهدفة عند الحاجة.
- شروط اعتماد الحيوان داخل القطيع الإنتاجي.

```text
تم نقل الحيوان → Workflow
الإشغال الحالي → Derived / Reports
قاعدة السماح بالتسكين → Settings
```

---

## 20. 6.5 قواعد التلقيح والخصوبة والجاهزية التناسلية — APPROVED

يشمل شروط الجاهزية، العمر/الوزن عند الحاجة، استخدام الذكر، عدد وتكرار وفواصل المحاولات، تعريف الفشل وحدوده، واختلاف القواعد حسب السلالة إذا ثبتت الحاجة.

الأرقام نفسها تحسم بالأسئلة.

---

## 21. 6.6 قواعد فحص الحمل والحمل وتجهيز الولادة — APPROVED

يشمل موعد ونافذة الفحص، إعادة الفحص، التأخير، مدة الحمل أو نطاقها، الموعد المتوقع للولادة، تجهيز بيت الولادة، والمتابعة قبل الولادة.

تسجيل نتيجة الفحص أو وقوع الولادة فعليًا → Workflow.

---

## 22. 6.7 قواعد الولادة والرضاعة وإعادة التلقيح — APPROVED

يشمل مدة الرضاعة، متابعة البطن، وزن المواليد، الاستعداد للفطام، إعادة تلقيح الأم أثناء الرضاعة أو التأجيل وإعادة التقييم.

النظام يجب أن يسمح بدراسة تداخل دورة تناسلية جديدة للأم مع استمرار رضاعة البطن، بدل افتراض State خطي واحد.

---

## 23. 6.8 قواعد الفطام والانتقال للتتبع الفردي — APPROVED

الفطام Boundary:

```text
Litter Tracking
↓
Individual Animal Tracking
```
