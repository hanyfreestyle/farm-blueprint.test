# Questionnaire Section Architecture Review

> هذا الملف هو **سجل المناقشات والقرارات المعمارية الخاصة بإعادة تنظيم أقسام الاستبيان** قبل بدء دورة الإجابات الجديدة.
>
> الهدف منه أن يشرح **لماذا** تم تقسيم الأقسام بهذه الطريقة، وما الذي نُقل أو أُعيدت تسميته، وما الذي أُلغي كقسم مستقل، وما الذي ما زال تحت المراجعة.
>
> هذا الملف **ليس خطة تنفيذ**. بعد اكتمال المراجعة واعتماد الشجرة كاملة، يتم استخراج Implementation Plan مستقل بخطوات تنفيذ واضحة من القرارات المسجلة هنا.
>
> المرجع الأعلى للحالة الحالية للمشروع:
>
> `docs/FARM_BLUEPRINT_PROJECT_CONTEXT.md`

---

## 1. سبب فتح المراجعة

قبل بدء دورة إجابات جديدة تقرر الاستفادة من أن قاعدة بيانات التطوير الحالية يعاد بناؤها باستخدام:

```bash
php artisan migrate:refresh --seed
```

وبالتالي توجد فرصة مناسبة لإعادة النظر في بنية الأقسام قبل تثبيت إجابات نريد الحفاظ عليها لاحقًا.

أهداف المراجعة:

1. جعل مسؤولية كل Main Section واضحة وغير متداخلة.
2. نقل أو دمج أو حذف الأقسام الفرعية الموجودة في مكان غير منطقي.
3. اكتشاف الأجزاء المفقودة قبل إنشاء الأسئلة.
4. منع تكرار نفس القرار بين أكثر من قسم.
5. جعل شجرة Question Seeders لاحقًا مطابقة لشجرة الأقسام.
6. توثيق سبب التقسيم حتى لا نعتمد على الذاكرة أثناء إنشاء الأسئلة أو كتابة الـRequirements.

---

## 2. حالات القرارات

تستخدم الحالات التالية داخل هذا الملف:

- **APPROVED** — قرار تمت الموافقة عليه ويمكن بناء الخطوات التالية عليه.
- **PROPOSED** — اقتراح تحت النقاش ولم يعتمد بعد.
- **TO REVIEW** — موضوع معروف يحتاج مراجعة مخصصة.
- **MOVED** — موضوع تم اعتماد نقله من قسم إلى قسم آخر.
- **REMOVED** — موضوع تم اعتماد حذفه كقسم مستقل مع الحفاظ على مضمونه في المكان الصحيح عند الحاجة.

لا يعتبر أي `PROPOSED` أو `TO REVIEW` Requirement نهائيًا.

---

## 3. قاعدة الفصل المعماري — APPROVED

تم اعتماد القاعدة التالية لتحديد مكان كل موضوع:

```text
What IS it?
→ Master Data / Farm Structure / Animal Data

What HAPPENED?
→ Workflow

What do we KNOW from what happened?
→ Reports / Analytics

What RULES control what should happen?
→ Settings
```

بصياغة عربية:

```text
ما هو الشيء أو الكيان؟
→ البيانات الأساسية / هيكل المزرعة / بيانات الحيوان

ما الذي حدث فعليًا؟
→ الحركات ودورة التشغيل

ماذا نعرض أو نستنتج من البيانات والحركات؟
→ التقارير والتحليلات والتنبيهات

ما القواعد التي تتحكم فيما يجب أن يحدث؟
→ الإعدادات وقواعد التشغيل
```

هذه القاعدة مرجع أساسي أثناء تصميم Subsections والأسئلة لاحقًا.

---

## 4. الهيكل الرئيسي المستهدف — APPROVED

تم اعتماد الهيكل التالي للمراجعة والتخطيط:

```text
1. إدارة البيانات الأساسية
2. هيكل المزرعة
3. بيانات الحيوان وتكوين القطيع
4. الحركات ودورة التشغيل الفعلية
5. التقارير والتحليلات والتنبيهات ومؤشرات الأداء
6. الإعدادات وقواعد التشغيل
```

**مهم:** هذا هو الهيكل المستهدف المعتمد، لكنه لم ينفذ بعد بالكامل في Section Seeders. التنفيذ يتم فقط بعد إنهاء مراجعة القسم السادس واستخراج Implementation Plan مستقل.

---

## 5. قرار جعل الإعدادات آخر قسم — APPROVED

القسم القديم:

`إعدادات التشغيل ودورة الإنتاج`

يتجه إلى أن يصبح:

`الإعدادات وقواعد التشغيل`

ويكون آخر Main Section.

السبب أن ترتيب الدراسة يجب أن يكون:

```text
الكيانات والبيانات
→ الحركات الفعلية
→ التقارير والمخرجات المطلوبة
→ ثم القواعد والإعدادات التي تتحكم في كل ما سبق
```

مثال: نفهم تقرير الخصوبة والمؤشرات المطلوبة أولًا، ثم نسأل لاحقًا عن أهدافه وحدوده وThresholds القابلة للإعداد.

# القسم الثالث — بيانات الحيوان وتكوين القطيع

## 6. الشجرة المعتمدة — APPROVED

```text
3. بيانات الحيوان وتكوين القطيع
│
├── 3.1 بيانات وهوية الحيوان
├── 3.2 مصدر الحيوان وبداية السجل
├── 3.3 النسب وشجرة العائلة
├── 3.4 القطيع الافتتاحي وتهيئة نقطة البداية
└── 3.5 تكوين القطيع الإنتاجي وتنظيم المجموعات
```

### لماذا تم تغيير القسم القديم؟

القسم القديم `تكوين وإدخال القطيع` كان يخلط بين:

- بيانات تأسيسية للحيوان.
- حركات تشغيلية.
- قواعد Settings.
- Outputs مشتقة تظهر في التقارير أو Dashboard.

بعد مراجعة Workflow أصبح لكل جزء مكان واضح.

### 6.1 بيانات وهوية الحيوان

يحدد Animal Record والبيانات الأساسية التي تستمر مع الحيوان طوال حياته.

لا تعامل القيم المشتقة من الأحداث كحقول يدوية ثابتة، مثل:

- الموقع الحالي.
- الوزن الحالي.
- الجاهزية الحالية.
- الحالة الإنتاجية الحالية.

### 6.2 مصدر الحيوان وبداية السجل

يجيب عن:

> من أين بدأت معرفة النظام بهذا الحيوان وما أول نقطة موثقة في سجله؟

مصادر محتملة يدعمها المرجع الوظيفي:

- إنتاج داخلي.
- مصدر خارجي.
- نقل بين المزارع عند وجود أكثر من مزرعة.

### 6.3 النسب وشجرة العائلة

يبقى مستقلًا مع الحفاظ على الفصل بين:

```text
Breed
= تعريف السلالة المرجعي في Master Data

Animal Pedigree
= الأب + الأم + علاقات القرابة + شجرة العائلة الفعلية للحيوان
```

### 6.4 القطيع الافتتاحي وتهيئة نقطة البداية

يعالج بدء استخدام النظام في مزرعة قائمة بالفعل قد تحتوي مثلًا على:

- أنثى حامل.
- أم مرضعة.
- ذكر مستخدم بالفعل.
- مرشحي إحلال.
- أرانب نمو أو تسمين.
- حالات صحية أو تشغيلية قائمة.

القاعدة الوظيفية:

> لا يتم اختراع تاريخ غير معروف؛ يبدأ النظام من أول معلومة موثوقة متاحة.

### 6.5 تكوين القطيع الإنتاجي وتنظيم المجموعات

التمييز المعتمد:

```text
مفهوم Production Group وتكوينه
→ بيانات الحيوان وتكوين القطيع

النسب المستهدفة وقواعد الجاهزية
→ Settings

تغيير ذكر / إضافة أنثى / إخراج حيوان / تعديل المجموعة أثناء التشغيل
→ Workflow
```

## 7. ما تم نقله من القسم الثالث — APPROVED

### MOVED → Workflow

- `الدخول الأول للمزرعة والتقييم الأولي`.
- `تسكين القطيع وإدارة الإشغال`.
- `تحويل إنتاج المزرعة إلى القطيع والإحلال الداخلي`.

### REMOVED ككتلة واحدة: جاهزية القطيع

تم توزيعها حسب المسؤولية:

```text
قواعد الجاهزية
→ Settings

التحول الفعلي أو القرار
→ Workflow

عرض الجاهزية وأسباب عدمها
→ Reports / Dashboard
```

# القسم الرابع — الحركات ودورة التشغيل الفعلية

## 8. تعريف مسؤولية Workflow — APPROVED

Workflow مسؤول عن:

> **كل حدث أو إجراء فعلي يحدث بمرور الوقت ويغير سجل الحيوان أو البطن أو دورة الإنتاج أو موقع الإيواء أو المهمة التشغيلية.**

لا يقتصر على الدورة التناسلية.

```text
Entity / Data
= من هو الحيوان؟ وما هو القفص؟

Workflow
= ماذا حدث للحيوان أو القفص أو البطن أو المهمة؟ ومتى؟ ولماذا؟ ومن نفذه؟
```

├── 4.3 الوزن والقياسات التشغيلية

├── 4.8 الفطام والتحول إلى التتبع الفردي
├── 4.9 النمو والفرز وإعادة التقييم
├── 4.10 تحديد المصير والاستبعاد من المسار

## 10. قرارات إعادة تنظيم Workflow القديم — APPROVED

- بدء دورة الأنثى + تكرار التلقيح → يندمجان تحت `التلقيح وإدارة المحاولات`.
- الجس وفحص الحمل + متابعة الحمل وتجهيز الولادة → يندمجان في مسار حمل واضح.
- الولادة → تبقى مستقلة.
- الرضاعة → تبقى وتتطور.
- إعادة تلقيح الأم أثناء الرضاعة → لا تبقى Subsection مستقلًا؛ تدخل ضمن تداخل دورات الأم.
- الفطام → يبقى مستقلًا لأنه يحول `Litter-based tracking` إلى `Individual tracking`.
- النمو والوزن والفرز → يبقى مع فصل حدث الوزن العام.
- `تنفيذ قرار المصير: الإحلال أو التسمين` → يتفكك إلى تحديد مصير ثم مسار إحلال ومسار تسمين.
- الحالات الاستثنائية → تبقى وتتطور كـEvents تغير المسار.
- الخروج النهائي → يتطور ليغطي الخروج وإعادة الدخول والحفاظ على الهوية.

# القسم الخامس — التقارير والتحليلات والتنبيهات ومؤشرات الأداء

## 12. تعريف مسؤولية القسم — APPROVED

القسم الخامس لا يسجل الحدث نفسه؛ بل يحول البيانات والأحداث المسجلة إلى معلومات وتحليل ومؤشرات وتنبيهات تساعد على الإدارة واتخاذ القرار.

الأسئلة التي يجيب عنها معماريًا:

```text
ما الوضع الحالي؟
هل يوجد شيء يحتاج انتباهًا؟
ماذا تعني البيانات التي سجلناها؟
هل الأداء يتحسن أم يتراجع؟
ما القرار الذي تساعدنا البيانات على اتخاذه؟
```

والفصل المعتمد:

```text
Workflow
= تسجيل الواقعة

Reports / Analytics
= فهم الواقعة وتجميعها ومقارنتها واكتشاف معناها

Settings
= القواعد والأهداف والحدود التي نستخدمها للحكم عليها
```

## 15. حدود أهم Subsections في Reports — APPROVED

### 15.1 لوحة التحكم ومتابعة التشغيل اليومي

تعرض ما يحتاج انتباه المستخدم الآن، مثل:

- ملخص القطيع.
- المهام المستحقة والمتأخرة.
- الأحداث المهمة.
- التنبيهات الحالية.

تنفيذ المهمة نفسها لا يحدث هنا؛ هو Workflow.

### 15.2 تقارير القطيع والجاهزية

تشمل تكوين القطيع وحركته ومراحله والجاهزية الحالية وأسباب عدم الجاهزية.

```text
قواعد الجاهزية → Settings
التحول الفعلي → Workflow
عرض الجاهزية → Reports
```

### 15.3 الخصوبة والتلقيح والحمل

تحلل المحاولات والجس ونتائج الحمل والنجاح والفشل وما يرتبط بها من مؤشرات.

حدود الحكم وThresholds القابلة للتخصيص → Settings.

### 15.4 الولادة والرضاعة والفطام

تغطي نتائج الولادة والبطن والبقاء والنفوق أثناء المراحل والأوزان والفطام.

### 15.5 النمو والأوزان والتسمين

تحلل سجلات الوزن ومنحنيات النمو ومعدلات الزيادة والتسمين والجاهزية للبيع.

### 15.6 الصحة والنفوق والعزل

تحلل الأحداث الصحية والنفوق والعزل والتجمعات غير الطبيعية حسب المرحلة والموقع والعوامل ذات الصلة.

### 15.7 تحليل أداء الحيوانات الإنتاجية

لا يعتمد على رقم واحد؛ يجمع مجموعة مؤشرات مناسبة للإناث والذكور والحيوانات الإنتاجية بما يساعد على قرارات الاستمرار أو الاستبعاد أو الإحلال.

### 15.8 النسب والإحلال

تشمل شجرة العائلة والقرابة والخطوط الوراثية وقرارات الإحلال ونتائجها لاحقًا.

### 15.9 الإشغال والسعة والمواقع

تعرض:

```text
Farm → Barn → Battery → Cage
Capacity / Occupancy / Available / Occupancy %
```

مع التحليل والتوقعات اللازمة عند الحاجة.

### 15.10 الاتجاهات والمقارنات والتحليل عبر الزمن

تجمع المقارنة عبر الزمن والمقارنة بين أجزاء المزرعة أو المجموعات في Capability واحدة بدل تكرارها في قسمين.

### 15.11 الصفحات والسجلات التحليلية

تجمع الصفحات التحليلية للكيانات تحت مبدأ:

```text
Entity
+ Timeline
+ Derived Indicators
+ Related Entities
+ Outcome
```

ولا يلزم إنشاء Subsection مستقل لكل صفحة تحليلية مستقبلية.

### 15.12 التنبيهات والإنذار المبكر

تغطي:

- الحالات التي يجب اكتشافها.
- المعلومات التي يعرضها التنبيه.
- تاريخ التنبيه ومراجعته وإغلاقه.
- الربط بالإجراء الناتج عند الحاجة.

لكن:

```text
Thresholds / Alert Severity / Priority Rules
→ Settings

الإجراء المنفذ نتيجة التنبيه
→ Workflow / Related Action
```

### 15.13 جودة البيانات والاستثناءات الإدارية

تعالج البيانات الناقصة أو المتعارضة التي قد تجعل التقارير مضللة، مثل مواقع مفقودة أو تناقضات بين الأحداث أو تجاوزات غير منطقية للسعة أو تسلسل التشغيل.

### 15.14 KPIs

تحدد مؤشرات الأداء التي نحتاجها وما الذي تقيسه.

أما Targets وThresholds والفترات القابلة للتخصيص → Settings عند الحاجة.

### 15.15 خصائص التقارير والتصفية والتصدير

Cross-cutting Reporting Capability تسأل مرة واحدة عن السلوك العام للتقارير مثل:

- التصفية.
- النطاقات الزمنية.
- التصدير.
- الطباعة.
- السلوك المشترك بين التقارير.

ولا تكرر هذه الأسئلة داخل كل Report Domain.

## 17. صلاحيات ونطاق الاطلاع على التقارير — OPEN REQUIREMENT

تم اكتشاف موضوع يحتاج أسئلة لاحقًا، لكن لا توجد معلومات كافية لاعتماد Architecture تفصيلية له الآن:

- هل يرى المستخدم كل المزارع أم المزارع المرتبط بها فقط؟
- هل يمكن تقييد التقارير حسب Farm / Barn / Role؟
- هل توجد تقارير تحتاج Permission مستقلة؟

هذا **ليس Requirement محسومًا** ويجب تحويله إلى أسئلة عند بناء `خصائص التقارير` أو جزء الصلاحيات المناسب.

## 20. قواعد استخدام هذا الملف أثناء إنشاء الأسئلة لاحقًا

عند إنشاء أسئلة أي Subsection بعد اعتماد الهيكل:

1. قراءة `FARM_BLUEPRINT_PROJECT_CONTEXT.md` أولًا.
2. مراجعة الجزء المقابل من `تصور_مشروع_الارانب.md`.
3. قراءة القسم المقابل من هذا الملف لفهم **سبب وجود Subsection وحدوده**.
4. مراجعة الأسئلة والقرارات السابقة لمنع التكرار.
5. التأكد أن السؤال يقع في المكان الصحيح حسب `Entity / Event / Output / Rule`.
6. عدم تحويل Open Requirement أو مثال إلى Requirement نهائي بدون سؤال أو قرار صريح.
7. بعد اعتماد الإجابات، تصبح الإجابات والـQuestionnaire Guides مصدر القرارات النهائية.

## 22. قاعدة إنشاء خطة التنفيذ لاحقًا

بعد اكتمال مراجعة القسم السادس واعتماد الشجرة النهائية:

1. لا يتم التنفيذ من الذاكرة أو من المحادثة.
2. يتم استخراج **Implementation Plan مستقل** من هذا الملف.
3. الخطة تحدد بالتسلسل:
   - تعديل أسماء وترتيب Main Sections.
   - تعديل Subsections.
   - التعامل مع Legacy Sections بأمان.
   - تحديث Section Seeders.
   - إنشاء/إعادة تنظيم Question Seeder folders.
   - إنشاء Orchestrators المطلوبة.
   - تحديث `FARM_BLUEPRINT_PROJECT_CONTEXT.md`.
   - تحديث `QUESTIONNAIRE_IMPLEMENTATION_PLAN.md` عند الحاجة.
   - تشغيل `php artisan migrate:refresh --seed` في مرحلة التطوير الحالية.
   - مراجعة الشجرة قبل بدء الإجابات.
4. بعد بدء الاحتفاظ بالإجابات، أي تعديل لاحق يراعي Stable IDs / Stable seed_keys / Stable option values و`preserveAnswers = true`.
