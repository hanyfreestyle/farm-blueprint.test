# Questionnaire Section Architecture Review

> هذا الملف هو **سجل المناقشات والقرارات المعمارية الخاصة بإعادة تنظيم أقسام الاستبيان** قبل بدء دورة الإجابات الجديدة.
>
> الهدف منه أن يشرح **لماذا** تم تقسيم الأقسام بهذه الطريقة، وما الذي نُقل أو أُعيدت تسميته أو دمجه أو أُلغي كقسم مستقل، حتى لا نعتمد على الذاكرة أثناء إنشاء الأسئلة أو كتابة الـRequirements.
>
> هذا الملف **ليس خطة تنفيذ**. بعد اكتمال المراجعة واعتماد الشجرة كاملة، يتم استخراج Implementation Plan مستقل بخطوات تنفيذ واضحة من القرارات المسجلة هنا.
>
> المرجع الأعلى للحالة الحالية للمشروع:
>
> `docs/FARM_BLUEPRINT_PROJECT_CONTEXT.md`

---

## 1. سبب فتح المراجعة

قبل بدء دورة إجابات جديدة تقرر الاستفادة من أن قاعدة بيانات التطوير الحالية يعاد بناؤها باستخدام:

```bash
php artisan migrate:refresh --seed
```

وبالتالي توجد فرصة مناسبة لإعادة النظر في بنية الأقسام قبل تثبيت إجابات نريد الحفاظ عليها لاحقًا.

أهداف المراجعة:

1. جعل مسؤولية كل Main Section واضحة وغير متداخلة.
2. نقل أو دمج أو حذف الأقسام الفرعية الموجودة في مكان غير منطقي.
3. اكتشاف الأجزاء المفقودة قبل إنشاء الأسئلة.
4. منع تكرار نفس القرار بين أكثر من قسم.
5. جعل شجرة Question Seeders لاحقًا مطابقة لشجرة الأقسام.
6. توثيق سبب التقسيم حتى لا نعتمد على الذاكرة أثناء إنشاء الأسئلة أو كتابة الـRequirements.

---

## 2. حالات القرارات

- **APPROVED** — قرار تمت الموافقة عليه ويمكن بناء الخطوات التالية عليه.
- **PROPOSED** — اقتراح تحت النقاش ولم يعتمد بعد.
- **TO REVIEW** — موضوع معروف يحتاج مراجعة مخصصة.
- **MOVED** — موضوع تم اعتماد نقله من قسم إلى قسم آخر.
- **REMOVED** — موضوع تم اعتماد حذفه كقسم مستقل مع الحفاظ على مضمونه في المكان الصحيح عند الحاجة.

لا يعتبر أي `PROPOSED` أو `TO REVIEW` Requirement نهائيًا.

## 3. قاعدة الفصل المعماري — APPROVED

```text
What IS it?
→ Master Data / Farm Structure / Animal Data

What HAPPENED?
→ Workflow

What do we KNOW from what happened?
→ Reports / Analytics

What RULES control what should happen?
→ Settings
```

بصياغة عربية:

```text
ما هو الشيء أو الكيان؟
→ البيانات الأساسية / هيكل المزرعة / بيانات الحيوان

ما الذي حدث فعليًا؟
→ الحركات ودورة التشغيل

ماذا نعرض أو نستنتج من البيانات والحركات؟
→ التقارير والتحليلات والتنبيهات

ما القواعد التي تتحكم فيما يجب أن يحدث؟
→ الإعدادات وقواعد التشغيل
```

هذه القاعدة مرجع أساسي أثناء تصميم Subsections والأسئلة لاحقًا.

## 4. الهيكل الرئيسي المستهدف — APPROVED

```text
1. إدارة البيانات الأساسية
2. هيكل المزرعة
3. بيانات الحيوان وتكوين القطيع
4. الحركات ودورة التشغيل الفعلية
5. التقارير والتحليلات والتنبيهات ومؤشرات الأداء
6. الإعدادات وقواعد التشغيل
```

### لماذا Settings هو آخر Main Section؟

القسم القديم:

`إعدادات التشغيل ودورة الإنتاج`

يتحول إلى:

`الإعدادات وقواعد التشغيل`

ويكون آخر Main Section لأن ترتيب الدراسة المعتمد هو:

```text
الكيانات والبيانات
→ الحركات الفعلية
→ التقارير والمخرجات المطلوبة
→ ثم القواعد والإعدادات التي تتحكم في كل ما سبق
```

الهدف أن نفهم أولًا ماذا يوجد، وما الذي يحدث، وما الذي نريد قياسه أو عرضه، ثم نسأل ما القيم والقواعد التي يجب أن تكون قابلة للتخصيص.

# القسم الثالث — بيانات الحيوان وتكوين القطيع

## 5. الشجرة المعتمدة — APPROVED

```text
3. بيانات الحيوان وتكوين القطيع
│
├── 3.1 بيانات وهوية الحيوان
├── 3.2 مصدر الحيوان وبداية السجل
├── 3.3 النسب وشجرة العائلة
├── 3.4 القطيع الافتتاحي وتهيئة نقطة البداية
└── 3.5 تكوين القطيع الإنتاجي وتنظيم المجموعات
```

### 5.1 بيانات وهوية الحيوان

يحدد Animal Record والبيانات الأساسية التي تستمر مع الحيوان طوال حياته.

لا تعامل القيم المشتقة من الأحداث كحقول يدوية ثابتة، مثل:

- الموقع الحالي.
- الوزن الحالي.
- الجاهزية الحالية.
- الحالة الإنتاجية الحالية.

### 5.2 مصدر الحيوان وبداية السجل

يجيب عن:

> من أين بدأت معرفة النظام بهذا الحيوان وما أول نقطة موثقة في سجله؟

مصادر محتملة يدعمها المرجع الوظيفي:

- إنتاج داخلي.
- مصدر خارجي.
- نقل بين المزارع عند وجود أكثر من مزرعة.

### 5.3 النسب وشجرة العائلة

الفصل المعتمد:

```text
Breed
= تعريف السلالة المرجعي في Master Data

Animal Pedigree
= الأب + الأم + علاقات القرابة + شجرة العائلة الفعلية للحيوان
```

### 5.4 القطيع الافتتاحي وتهيئة نقطة البداية

يعالج بدء استخدام النظام في مزرعة قائمة بالفعل قد تحتوي مثلًا على:

- أنثى حامل.
- أم مرضعة.
- ذكر مستخدم بالفعل.
- مرشحي إحلال.
- أرانب نمو أو تسمين.
- حالات صحية أو تشغيلية قائمة.

القاعدة الوظيفية:

> لا يتم اختراع تاريخ غير معروف؛ يبدأ النظام من أول معلومة موثوقة متاحة.

### 5.5 تكوين القطيع الإنتاجي وتنظيم المجموعات

```text
مفهوم Production Group وتكوينه
→ بيانات الحيوان وتكوين القطيع

النسب المستهدفة وقواعد الجاهزية
→ Settings

تغيير ذكر / إضافة أنثى / إخراج حيوان / تعديل المجموعة أثناء التشغيل
→ Workflow
```

## 6. ما تم نقله من القسم الثالث — APPROVED

### MOVED → Workflow

- `الدخول الأول للمزرعة والتقييم الأولي`.
- `تسكين القطيع وإدارة الإشغال`.
- `تحويل إنتاج المزرعة إلى القطيع والإحلال الداخلي`.

### REMOVED ككتلة واحدة: جاهزية القطيع

```text
قواعد الجاهزية
→ Settings

التحول الفعلي أو القرار
→ Workflow

عرض الجاهزية وأسباب عدمها
→ Reports / Dashboard
```

# القسم الرابع — الحركات ودورة التشغيل الفعلية

## 7. تعريف مسؤولية Workflow — APPROVED

Workflow مسؤول عن:

> **كل حدث أو إجراء فعلي يحدث بمرور الوقت ويغير سجل الحيوان أو البطن أو دورة الإنتاج أو موقع الإيواء أو المهمة التشغيلية.**

لا يقتصر على الدورة التناسلية.

```text
Entity / Data
= من هو الحيوان؟ وما هو القفص؟

Workflow
= ماذا حدث للحيوان أو القفص أو البطن أو المهمة؟ ومتى؟ ولماذا؟ ومن نفذه؟
```

## 8. الشجرة المعتمدة لـWorkflow — APPROVED

```text
4. الحركات ودورة التشغيل الفعلية
│
├── 4.1 استقبال الحيوان من الخارج وإعادة الإدخال
├── 4.2 التسكين والنقل والإخلاء وإدارة الإشغال
├── 4.3 الوزن والقياسات التشغيلية
├── 4.4 التلقيح وإدارة المحاولات
├── 4.5 فحص الحمل ومتابعة الحمل وتجهيز الولادة
├── 4.6 تسجيل الولادة وإنشاء البطن
├── 4.7 الرضاعة ومتابعة البطن وتداخل دورات الأم
├── 4.8 الفطام والتحول إلى التتبع الفردي
├── 4.9 النمو والفرز وإعادة التقييم
├── 4.10 تحديد المصير والاستبعاد من المسار
├── 4.11 الإحلال والاعتماد داخل القطيع الإنتاجي
├── 4.12 التسمين والجاهزية للبيع
├── 4.13 الصحة والعزل والتعافي والنفوق
├── 4.14 الحالات الاستثنائية وإعادة بناء المسار
├── 4.15 الخروج من المزرعة وإعادة الدخول
├── 4.16 تشغيل وصيانة وتجهيز مواقع الإيواء
└── 4.17 تنفيذ وإدارة المهام التشغيلية
```

هذه الشجرة معتمدة كأساس لخطة التنفيذ وإنشاء الأسئلة لاحقًا. يمكن تحسين الصياغة أثناء Implementation Plan بشرط عدم حذف نطاق وظيفي دون مناقشة جديدة.

## 9. قرارات إعادة تنظيم Workflow القديم — APPROVED

- بدء دورة الأنثى + تكرار التلقيح → `التلقيح وإدارة المحاولات`.
- الجس وفحص الحمل + متابعة الحمل وتجهيز الولادة → مسار حمل واحد واضح.
- الولادة → تبقى مستقلة.
- الرضاعة → تبقى وتتطور.
- إعادة تلقيح الأم أثناء الرضاعة → جزء من تداخل دورات الأم، وليس Subsection مستقلًا.
- الفطام → يبقى مستقلًا لأنه يحول `Litter-based tracking` إلى `Individual tracking`.
- النمو والوزن والفرز → يبقى مع فصل حدث الوزن العام.
- `تنفيذ قرار المصير: الإحلال أو التسمين` → يتفكك إلى تحديد مصير ثم مسار إحلال ومسار تسمين.
- الحالات الاستثنائية → Events تغير المسار وتحفظ التاريخ.
- الخروج النهائي → يتطور ليغطي الخروج وإعادة الدخول والحفاظ على الهوية.

## 10. قواعد الفصل المرتبطة بـWorkflow — APPROVED

### الوزن

```text
تسجيل وزن أو قياس فعلي → Workflow
موعد الوزن والمستهدف وحدود التنبيه → Settings
منحنيات النمو والتحليل → Reports / Analytics
```

### المهام

```text
قواعد توليد المهمة وموعدها وأولويتها → Settings
إنشاء/تنفيذ/تأجيل/إلغاء/إغلاق المهمة وتسجيل النتيجة → Workflow
عرض مهام اليوم والمتأخرات → Dashboard / Reports
```

### الجاهزية

```text
قواعد الجاهزية → Settings
تنفيذ انتقال أو قرار فعلي → Workflow
عرض الجاهزية وأسباب عدمها → Reports / Dashboard
```

### المواقع والإشغال

```text
تعريف Farm / Barn / Battery / Cage → Farm Structure
التسكين / النقل / الإخلاء / الصيانة / التطهير / العودة للخدمة → Workflow
قواعد السعة والإتاحة والتطهير → Settings
عرض الإشغال والسعة والحالات الحالية → Reports / Analytics
```

تم اعتماد إبقاء حركات المواقع وLifecycle المهام داخل Workflow بدل إنشاء Main Sections مستقلة لأنها كلها تجيب عن: **ما الذي حدث فعليًا؟**

## 11. تعريف مسؤولية القسم — APPROVED

القسم الخامس لا يسجل الحدث نفسه؛ بل يحول البيانات والأحداث المسجلة إلى معلومات وتحليل ومؤشرات وتنبيهات تساعد على الإدارة واتخاذ القرار.

## 13. قرارات إعادة تنظيم Reports — APPROVED

- `المهام والتنبيهات اليومية` → العرض اليومي في Dashboard/Alerts؛ تنفيذ المهمة في Workflow.
- `تقارير القطيع` → تتطور لتشمل الجاهزية.
- `تقارير الخصوبة والتلقيح` → تتوسع لتشمل الحمل.
- `تقارير النفوق والصحة` → تتوسع لتشمل العزل.
- `تقييم أداء الإناث والذكور` → `تحليل أداء الحيوانات الإنتاجية`.
- التقارير المقارنة والاتجاهات الزمنية + المقارنة بين أجزاء المزرعة → نطاق تحليلي واحد.
- صفحة الحيوان التحليلية + صفحة البطن التحليلية → `الصفحات والسجلات التحليلية`.
- سجل التنبيهات → يندمج مع الإنذار المبكر مع الحفاظ على التاريخ.
- `مستويات التنبيه` → **MOVED إلى Settings**.
- التصفية والتصدير → Cross-cutting Reporting Capability.
- `التقرير → التنبيه → القرار → الإجراء` → **REMOVED كـSubsection** ويصبح مبدأ معماريًا.

## 14. مبدأ التقرير → التنبيه → القرار → الإجراء — APPROVED

```text
Data
↓
Information / Analysis
↓
Alert عند الحاجة
↓
Decision
↓
Action
↓
Result
↓
Data جديدة
```

### فصل التنبيهات

```text
الحالة التي يجب اكتشافها + تاريخ التنبيه وعرضه → Reports / Analytics
Threshold / Severity / Priority Rules → Settings
الإجراء المنفذ نتيجة التنبيه → Workflow / Related Action
```

### فصل KPIs

```text

```

### OPEN REQUIREMENT

صلاحيات ونطاق الاطلاع على التقارير لم تحسم بعد، ويجب تحويلها إلى أسئلة عند بناء `خصائص التقارير` أو جزء الصلاحيات المناسب.

# القسم السادس — الإعدادات وقواعد التشغيل

## 15. منهج بناء Settings من الأقسام 1–5 — APPROVED

Settings لا يعتمد على Seeder القديم وحده ولا على الأقسام 3–5 فقط.

يجب مراجعة الأقسام **1–5 كلها** لاستخراج أي Rule قابل للتخصيص، بما في ذلك Master Data وFarm Structure.

لكن لا ينقل كل Business Rule تلقائيًا إلى Settings.

```text
Structural / System Rule
= قاعدة ثابتة ناتجة من تصميم الـBlueprint أو تعريف الكيان

Operational Setting
= قاعدة تشغيل نريد أن تكون قابلة للضبط أو الاختلاف حسب نطاق التطبيق

Runtime Event / Decision
= ما حدث فعليًا نتيجة تطبيق القواعد
```

مثال:

```text
فريدة كود القفص وهوية القفص → Structural / System Rule
فترة الانتظار بعد التطهير → Operational Setting إذا اعتمد أنها قابلة للتخصيص
تم تطهير القفص في تاريخ معين → Workflow Event
```

الهدف هو منع تحويل القسم السادس إلى مكان يجمع كل Rule موجود في المشروع حتى لو كان قاعدة ثابتة لا ينبغي للمستخدم تعديلها.

## 17. 6.1 نموذج الإعدادات ونطاق التطبيق — APPROVED

وظيفته **تعريف Architecture منظومة الإعدادات نفسها**، وليس تحديد قيم التلقيح أو الفطام أو السعة أو التنبيهات.

المبادئ المعتمدة:

```text
Structural / System Rule ≠ Operational Setting
Operational Settings may have a Scope
Settings changes must be historically explainable
```

### ما يجب حسمه بالأسئلة

- هل Settings على مستوى System أو Farm أو Barn أو Profile؟
- ما العلاقة بين Farm / Barn / Operational Settings Profile؟
- هل Profile قابل لإعادة الاستخدام بين أكثر من Barn؟
- هل يوجد Farm Default؟
- هل يوجد Inheritance؟
- هل يسمح بـOverrides؟
- هل يمكن وجود أكثر من Profile فعال؟
- هل يستخدم Effective Date؟
- هل كل تعديل ينشئ Version جديدًا؟
- ماذا يحدث للعمليات الجارية والمهام القائمة عند تعديل الإعدادات؟
- هل تحتفظ الأحداث بمرجع أو Snapshot للإعدادات السارية وقت التنفيذ؟
- من يملك صلاحية تعديل أو اعتماد Settings؟

هذه **Open Requirements** وليست افتراضات.

### مبدأ التاريخ

> **تغيير الإعدادات لا يجوز أن يجعل الماضي يُفسر باستخدام قيمة حالية مختلفة عن السياق الذي حدث فيه.**

الطريقة التقنية النهائية لا تزال سؤالًا مفتوحًا: History / Effective Date / Versioned Profile / Profile جديد / Reference أو Snapshot مناسب.

## 18. 6.2 السياسات العامة والتحكم والتجاوز والتدقيق — APPROVED

```text

```

### ما يبقى مع Entity

- طريقة الهوية الأساسية.
- Unique Scope.
- حالات Lifecycle الخاصة بالكيان.
- العلاقات الهيكلية.
- Delete / Retirement Policy.
- Fixed/Managed Master Data Lists وInitial Values وRetirement Policy.

### ما يدخل 6.2

- الجزء القابل للتهيئة من Code Generation عند الحاجة: Format / Prefix / Sequence / Scope / Reset.


- Override Policy.
- الفرق بين Action Permission وOverride Permission.
- Sensitive Record Correction.
- Minimum Audit Trail.

بعض القواعد قد تكون Hard System Constraints ولا تسمح Override.
