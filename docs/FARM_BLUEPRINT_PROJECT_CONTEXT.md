# Farm Blueprint — Project Context & Working Rules

## 1. تعريف المشروع

المستودع الأساسي:

`hanyfreestyle/farm-blueprint.test`

هذا المشروع **ليس نظام إدارة مزرعة الأرانب النهائي**.

وظيفته هي بناء **Blueprint / دراسة تحليلية تفصيلية** قبل تطوير النظام الفعلي، وتحويل التصور النظري ودورة العمل إلى:

**أقسام → أقسام فرعية → أسئلة تحليلية → إجابات → قرارات ومتطلبات → تقارير فنية → Blueprint قابل للتنفيذ.**

الهدف من الأسئلة ليس جمع معلومات عامة، بل الوصول إلى **Software Requirements وBusiness Rules** واضحة.

---

## 2. التقنية المستخدمة

المشروع مبني حاليًا باستخدام:

- Laravel 12
- PHP 8.2
- Filament 4
- MySQL
- Questionnaire Engine مخصص للمشروع
- `spatie/laravel-translatable` للبيانات متعددة اللغات عند الحاجة

---

## 3. الهيكل المنطقي للدراسة

الدراسة مقسمة حاليًا إلى الأقسام الرئيسية التالية:

1. إدارة البيانات الأساسية — Master Data / Foundation.
2. إعدادات التشغيل — Operation Settings.
3. تكوين وإدخال القطيع — Herd Setup.
4. الحركات ودورة التشغيل — Workflow.
5. التقارير والإشعارات ومؤشرات الأداء — Reports.

القسم الأول يمثل الـFoundation الذي تعتمد عليه بقية أجزاء النظام.

---

## 4. طريقة إنشاء الأقسام

المصدر الأساسي للأقسام هو:

`database/seeders/Sections/`

ويتم استدعاؤها من:

`QuestionnaireSectionSeeder`

كل Section Seeder مسؤول عن إنشاء القسم الرئيسي والأقسام الفرعية ووصفها وترتيبها.

يجب الحفاظ على هوية الأقسام الحالية قدر الإمكان وعدم إنشاء نسخ مكررة عند تغيير الاسم أو إعادة تشغيل Seeder، خصوصًا بعد وجود أسئلة أو إجابات مرتبطة بها.

إدارة البيانات الأساسية

`إدارة البيانات الأساسية`

بدل إنشاء Main Section جديد مكرر.

## 6. بيانات المزرعة — قرارات تأسيسية محسومة

عند بناء أسئلة بيانات المزرعة يجب البدء بسؤالين أساسيين:

1. ما الحقول التي يجب أن يحتوي عليها ملف المزرعة؟
2. أي من هذه الحقول يجب أن يكون إلزاميًا؟

الهدف من السؤال الأول هو تحديد **Migration Fields / Relationships**، ومن السؤال الثاني تحديد **Required / Nullable / Validation Rules**.

### الموقع الجغرافي للمزرعة

الموقع المعتمد وظيفيًا يتكون من:

- المحافظة.
- المدينة.
- العنوان.
- الموقع على الخريطة.

لا حاجة لتكرار أسئلة منفصلة عن تفاصيل الموقع بعد اعتماد هذه العناصر، إلا إذا ظهرت لاحقًا نقطة تصميمية غير محسومة فعلًا.

### بيانات الاتصال

يجب أن يدعم ملف المزرعة:

- أكثر من رقم هاتف.
- رقم واتساب أو أكثر عند الحاجة.

لا يتم افتراض أن التصميم النهائي سيكون أعمدة ثابتة مثل `phone_1` و`phone_2`؛ المطلوب وظيفيًا هو دعم تعدد بيانات الاتصال، ويتم حسم الشكل التنفيذي النهائي في الـBlueprint.

### المالك والمسؤولون

لا توجد حاجة حاليًا إلى تأسيس مفهوم "مالك المزرعة" كحقل تشغيلي رئيسي.

المسؤولون عن التشغيل هم **Users / أعضاء فريق تشغيل** لديهم حق تسجيل الدخول إلى لوحة التحكم.

---

## 7. المستخدمون وفريق التشغيل والورديات

هذا الجزء يعتبر من الـFoundation منذ البداية لأنه يؤثر لاحقًا على التشغيل والمهام والتنبيهات والتدقيق.

المبادئ الحالية:

- عضو فريق التشغيل هو User يمكنه تسجيل الدخول إلى لوحة التحكم.
- يمكن ربط المستخدم بالمزرعة أو المزارع التي يعمل عليها.
- يمكن أن يكون للمستخدم دور وصلاحيات تحدد ما يستطيع رؤيته أو تنفيذه.
- يجب دعم مفهوم الورديات / Shifts ضمن التحليل.
- ربط المستخدم بالمزرعة يجب أن يساعد لاحقًا في تحديد نطاق وصوله إلى ما يتبعها مثل العنابر والبطاريات والأقفاص والعمليات.
- عند تصميم السجل التاريخي يجب الانتباه إلى أن وردية المستخدم الحالية قد تتغير مستقبلًا، لذلك لا ينبغي فقد سياق الوردية التي تمت خلالها العملية إذا قررنا أن هذا السياق مطلوب للتدقيق.

القرارات التفصيلية الخاصة بعلاقة User ↔ Farm ↔ Shift ↔ Permissions ستُحسم من خلال أسئلة القسم الجديد.

## 8. المحافظات والمدن

المحافظات والمدن Master Data مستقلة.

العلاقة الأساسية:

```text
Governorate
    ↓ 1:N
City
```

وعند اختيار موقع المزرعة يجب أن تكون المدينة متوافقة مع المحافظة التابعة لها.

كل من المحافظات والمدن ستكون Module / Table مستقلة في النظام النهائي.

---

## 9. قوائم الأسباب التشغيلية

القوائم التالية تم اعتمادها كـMaster Data مستقلة منذ البداية:

- أسباب النقل.
- أسباب النفوق.
- أسباب الاستبعاد.
- أسباب الخروج.
- أسباب تغيير الذكر.

كل واحدة منها يجب أن تكون:

- Module مستقل.
- Table مستقل.
- قابلة للإدارة من لوحة التحكم.
- مرتبطة بالسجلات التشغيلية عن طريق `id` وForeign Keys.
- لا تعتمد على `code` كهوية للعلاقة.

الحد الأدنى المقترح لبنية هذه القوائم عند مرحلة تصميم قاعدة البيانات:

```text
id
name (JSON / translatable)
is_active
sort_order
created_at
updated_at
```

وجود `is_active` مهم حتى يمكن إيقاف قيمة من الاختيارات الجديدة بدون حذفها وكسر السجلات التاريخية التي استخدمتها سابقًا.

---

## 10. قاعدة تعدد اللغات

النظام النهائي يجب أن يدعم **العربية والإنجليزية** في لوحة التحكم وفي المدخلات والمخرجات التي تحتاج عرضًا مترجمًا.

أي اسم أو وصف أو قيمة إدارية قابلة للعرض للمستخدم باللغتين يجب تصميمها كحقل **Translatable JSON** بدل إنشاء أعمدة منفصلة مثل:

```text
name_ar
name_en
```

النمط المطلوب يكون مثلًا:

```json
{
    "ar": "الإسكندرية",
    "en": "Alexandria"
}
```

وينطبق هذا المبدأ على أمثلة مثل:

- المحافظات.
- المدن.
- السلالات.
- أسباب النقل.
- أسباب النفوق.
- أسباب الاستبعاد.
- أسباب الخروج.
- أسباب تغيير الذكر.
- وأي Master Data أو اسم وصفي مشابه يتم اعتماده لاحقًا.

ليس كل حقل في النظام Translatable؛ الأرقام والتواريخ والـIDs والإحداثيات والقيم التقنية لا تحتاج ترجمة.

يجب مراجعة كل Migration مستقبلًا للتأكد من تطبيق هذا المبدأ على الحقول الوصفية الصحيحة.

---

## 11. قاعدة العلاقات والهوية في النظام النهائي

العلاقات بين الكيانات تعتمد على:

**IDs + Foreign Keys**

ولا تعتمد على الأكواد النصية كبديل للعلاقات.

أمثلة:

```text
cities.governorate_id
farm / location relation → city_id حسب التصميم النهائي
mortality record → mortality_reason_id
transfer record → transfer_reason_id
exclusion record → exclusion_reason_id
```

يمكن وجود أكواد في كيانات معينة إذا ظهرت لها فائدة تشغيلية مستقلة، لكن **الكود ليس أساس الربط بين الجداول**.

---

## 12. Master Data تظهر لاحقًا ولا يلزم نقلها كلها للقسم الأول

عند مراجعة `تصور_مشروع_الارانب.md` ظهرت بيانات مرجعية أخرى مهمة مثل:

- مراحل النمو والفرز.
- مصادر تكوين القطيع.
- قوائم أو أسباب تشغيلية إضافية قد تظهر مع دورة العمل.

لكن لا يجب نقل كل إعداد تشغيلي إلى القسم الأول.

القاعدة:

- ما يمثل Foundation مشتركًا ويحتاجه أكثر من جزء مبكرًا يؤسس ضمن إدارة البيانات الأساسية.
- ما يرتبط بمرحلة تشغيلية محددة يبقى داخل قسمه الطبيعي، حتى لو كان في النظام النهائي Module أو Master Data مستقلًا.

## 13. طريقة إنشاء الأسئلة

الأسئلة يتم إنشاؤها من خلال Seeders داخل:

`database/seeders/Questions/`

ويفضل أن يكون لكل Subsection Seeder مستقل قدر الإمكان.

السؤال يمكن أن يحتوي على:

- `title`
- `help_text`
- `type`
- `is_required`
- `sort_order`
- `report_category`
- `target_entity`
- `options`
- Dependencies

---

## 14. أنواع الأسئلة

يجب دائمًا مراجعة:

`App\Enums\Questionnaire\QuestionType`

قبل استخدام نوع جديد.

الأنواع الحالية تشمل:

- `text`
- `textarea`
- `number`
- `date`
- `yes_no`
- `single_choice`
- `multi_choice`
- `select`

لا يتم افتراض Question Type غير موجود في الكود.

---

## 15. Dependencies

يجب مراجعة:

`QuestionDependencyOperator`

قبل استخدام أي Operator.

الموجود حاليًا:

- EQUALS
- CONTAINS

الـSeeder قد يستخدم:

```text
depends_on_sort_order
dependency_operator
dependency_value
```

ثم يحول `depends_on_sort_order` إلى `depends_on_question_id` بعد إنشاء السؤال السابق.

## 17. الملف المرجعي الوظيفي الأساسي

الملف:

`تصور_مشروع_الارانب.md`

هو **Source of Reference** لدورة العمل ومتطلبات نظام إدارة مزرعة الأرانب.

عند إنشاء أو مراجعة أسئلة جديدة يجب:

1. قراءة الجزء المقابل من الملف.
2. الحفاظ على المصطلحات والمنطق الموجودين فيه.
3. مراجعة الأسئلة الموجودة حاليًا.
4. تحديد ما تم حسمه بالفعل وعدم إعادة سؤاله بدون داعٍ.
5. تحويل النقاط غير المحسومة إلى أسئلة تؤدي إلى قرار تصميمي أو تشغيلي واضح.
6. عدم اختراع متطلبات غير مدعومة بالمحتوى وكأنها حقائق من المشروع.
7. إذا احتاجت نقطة إلى بحث خارجي فيجب فصل البحث الخارجي بوضوح عن المرجع.

لا يتم تعديل `تصور_مشروع_الارانب.md` إلا بطلب صريح من المستخدم.

## 18. فلسفة إنشاء الأسئلة

الهدف ليس زيادة عدد الأسئلة.

كل سؤال يجب أن ينتج قرارًا مفيدًا، مثل:

- ما البيانات المطلوبة؟
- ما البيانات الإلزامية؟
- هل القيمة ثابتة أم قابلة للإدارة؟
- ما العلاقة بين الكيانات؟
- هل الإجراء إلزامي أم اختياري؟
- هل القاعدة تمنع العملية أم تعرض Warning فقط؟
- ما الحالات الممكنة؟
- ما الأحداث التي تغير Workflow؟
- ما الذي يولد Task أو Alert؟
- ما البيانات التاريخية التي يجب الاحتفاظ بها؟

**ليس كل Requirement يحتاج Question.**

إذا كان المرجع أو المستخدم قد حسم القرار بالفعل، يتم اعتباره Requirement للـBlueprint بدل إعادة فتحه كسؤال بلا فائدة.

## 19. قاعدة مهمة بخصوص Seeders والإجابات

بعض Question Seeders الحالية كانت تستخدم:

```php
$question->options()->delete();
```

ثم تعيد إنشاء الخيارات.

هذا الأسلوب قد يكون تدميريًا بعد وجود إجابات فعلية.

لذلك:

- لا يتم حذف خيارات مستخدمة تاريخيًا بصورة عمياء.
- لا يتم تغيير `value` لخيارات قد ترتبط بإجابات بدون دراسة الأثر.
- يجب الحفاظ على الإجابات الحالية عند إعادة تشغيل Seeders.
- أي تعديل قد يؤدي إلى فقد البيانات يحتاج تنبيهًا صريحًا قبل تنفيذه.

### الحالة الحالية للأسئلة

تم **تعطيل استدعاء `QuestionnaireFarmQuestionsSeeder` مؤقتًا من `DatabaseSeeder`** أثناء إعادة تصميم أسئلة القسم الأول.

ملفات الأسئلة القديمة لم تُحذف، ولم يتم تنفيذ أي حذف تلقائي للأسئلة أو الإجابات الموجودة في قواعد البيانات الحالية.

عند `migrate:fresh --seed` في الحالة الحالية لن يتم توليد أسئلة Farm القديمة من `DatabaseSeeder`.

## 20. قاعدة الحفاظ على الهوية

يجب الحفاظ قدر الإمكان على Identifier مستقر لعناصر الـQuestionnaire، خصوصًا:

- Sections.
- Questions.
- Options.

لا ينبغي الاعتماد على النص الظاهر وحده على المدى الطويل إذا كان تعديل الصياغة قد يكسر العلاقات أو الإجابات.

---

## 21. قواعد العمل مع GitHub

المستودع يتم التعامل معه افتراضيًا كـ:

**READ ONLY**

يسمح بالقراءة والبحث والتحليل ومراجعة الملفات واقتراح التعديلات فقط.

لا يتم تنفيذ أي تعديل أو إنشاء/حذف ملف أو Commit أو Branch أو Pull Request أو تعديل Seeder من تلقاء ChatGPT.

**وجود صلاحية الكتابة لا يعني وجود إذن بالتعديل.**

أي تعديل فعلي على GitHub يحتاج إلى طلب صريح ومباشر من المستخدم.

إذا لم يوجد طلب صريح، يكون العمل:

**قراءة + تحليل + اقتراح فقط.**

## 23. مزامنة GitHub مع النسخة المحلية

المستخدم يعمل على نسخة Local من المشروع.

طريقة العمل المفضلة هي إنهاء تعديلات المرحلة على GitHub ثم سحب جميع ملفات المرحلة مرة واحدة.

قبل السحب يفضل:

```bash
git status
```

ثم:

```bash
git pull origin master
```

خصوصًا يجب الانتباه إلى أي تعديلات Local غير محفوظة في Commit قبل تنفيذ `git pull`.

## 24. المبدأ الأساسي

هذا المشروع هو:

**أداة تحليل متطلبات قبل التطوير**

وليس:

**نظام المزرعة النهائي.**

الهدف النهائي هو Blueprint موثق ومنظم يقلل الافتراضات والقرارات غير المحسومة قبل بدء بناء نظام إدارة مزرعة الأرانب الحقيقي.
