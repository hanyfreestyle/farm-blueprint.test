# Farm Blueprint — Project Context & Working Rules

## 1. تعريف المشروع

المستودع الأساسي:

`hanyfreestyle/farm-blueprint.test`

هذا المشروع **ليس نظام إدارة مزرعة الأرانب النهائي**.

وظيفته بناء **Blueprint / دراسة تحليلية تفصيلية** قبل تطوير النظام الفعلي، وتحويل التصور ودورة العمل إلى:

```text
أقسام
→ أقسام فرعية
→ أسئلة
→ إجابات
→ مراجعة
→ قرارات ومتطلبات
→ Software Requirements / Business Rules
→ Blueprint قابل للتنفيذ
```

الهدف من الأسئلة هو الوصول إلى قرارات تصميمية وتشغيلية موثقة، وليس جمع معلومات عامة فقط.

## 2. المراجع الحية للمشروع

### المرجع الأساسي للحالة الحالية

`docs/FARM_BLUEPRINT_PROJECT_CONTEXT.md`

هذا الملف يجب أن يظل محدثًا مع كل قرار معماري أو تنظيمي معتمد، ولا يجوز تركه يعكس وضعًا أقدم من القرار أو الكود الحالي.

### سجل مراجعة معمارية الأقسام

`docs/QUESTIONNAIRE_SECTION_ARCHITECTURE_REVIEW.md`

هذا الملف يسجل **المناقشات وأسباب التقسيم والقرارات المقترحة والمعتمدة أثناء إعادة تصميم الأقسام** قبل دورة الإجابات الجديدة.

يجب الرجوع إليه عند:

- مراجعة Main Sections أو Subsections.
- نقل موضوع من قسم إلى آخر.
- إنشاء أسئلة في الأقسام التي خضعت لإعادة التقسيم.
- فهم لماذا وُضع موضوع معين في `Data` أو `Workflow` أو `Reports` أو `Settings`.
- إعداد خطة التنفيذ النهائية لإعادة الهيكلة.

هذا الملف **ليس Implementation Plan**؛ بعد اكتمال المراجعة سيتم استخراج خطة تنفيذ مستقلة منه.

### سجل التنفيذ والتاريخ التقني

`docs/QUESTIONNAIRE_IMPLEMENTATION_PLAN.md`

يحفظ تاريخ بناء أداة الاستبيان والمراحل والقرارات التقنية السابقة.

### أولوية المصادر عند التعارض

```text
أحدث قرار صريح معتمد من المستخدم
→ FARM_BLUEPRINT_PROJECT_CONTEXT.md
→ القرار المعتمد داخل QUESTIONNAIRE_SECTION_ARCHITECTURE_REVIEW.md
→ الكود الحالي
→ السجل التاريخي القديم
```

## 4. حالة الهيكل الرئيسي للدراسة

### 4.1 الوضع المنفذ حاليًا في Section Seeders

الكود الحالي ما زال يبني الأقسام الرئيسية التالية:

```text
1. إدارة البيانات الأساسية
2. هيكل المزرعة
3. إعدادات التشغيل ودورة الإنتاج
4. تكوين وإدخال القطيع
5. الحركات ودورة التشغيل الفعلية
6. التقارير والإشعارات ومؤشرات الأداء
```

### 4.2 الهيكل المستهدف المعتمد — لم ينفذ بعد

تمت الموافقة على الهيكل المستهدف التالي قبل إعادة بناء Seeders الأقسام:

```text
1. إدارة البيانات الأساسية
2. هيكل المزرعة
3. بيانات الحيوان وتكوين القطيع
4. الحركات ودورة التشغيل الفعلية
5. التقارير والتحليلات والتنبيهات ومؤشرات الأداء
6. الإعدادات وقواعد التشغيل
```

**مهم:** لا يتم تعديل Section Seeders إلى هذا الشكل النهائي قبل استكمال مراجعة Subsections للأقسام المتبقية وإنشاء خطة تنفيذ واضحة من ملف:

`docs/QUESTIONNAIRE_SECTION_ARCHITECTURE_REVIEW.md`

### 4.3 قاعدة الفصل المعماري الجديدة

عند تحديد مكان أي موضوع نستخدم القاعدة:

```text
What IS it?
→ Master Data / Farm Structure / Animal Data

What HAPPENED?
→ Workflow

What do we KNOW from what happened?
→ Reports / Analytics

What RULES control what should happen?
→ Settings
```

هذه القاعدة مرجع أساسي لمنع التداخل والتكرار بين الأقسام.

## 7. القسم الثالث المستهدف — بيانات الحيوان وتكوين القطيع — APPROVED

القسم الحالي في الكود ما زال باسم:

`تكوين وإدخال القطيع`

لكن الهيكل المستهدف المعتمد هو:

```text
بيانات الحيوان وتكوين القطيع
├── بيانات وهوية الحيوان
├── مصدر الحيوان وبداية السجل
├── النسب وشجرة العائلة
├── القطيع الافتتاحي وتهيئة نقطة البداية
└── تكوين القطيع الإنتاجي وتنظيم المجموعات
```

### قرارات النقل المعتمدة من الشجرة القديمة

- `الدخول الأول للمزرعة والتقييم الأولي` → **MOVED إلى Workflow**.
- `تسكين القطيع وإدارة الإشغال` → **MOVED إلى Workflow**.
- `تحويل إنتاج المزرعة إلى القطيع والإحلال الداخلي` → **MOVED إلى Workflow**.
- `جاهزية القطيع` → **REMOVED ككتلة واحدة** وموزعة كالتالي:
  - قواعد الجاهزية → Settings.
  - تنفيذ القرار أو الانتقال → Workflow.
  - عرض الجاهزية وأسباب عدمها → Reports / Dashboard.

هذه الشجرة معتمدة كأساس لخطة التنفيذ، لكنها لم تنفذ بعد في Section Seeder.

التفاصيل والأسباب موثقة في:

`docs/QUESTIONNAIRE_SECTION_ARCHITECTURE_REVIEW.md`

## 8. القسم الرابع المستهدف — الحركات ودورة التشغيل الفعلية — APPROVED

### تعريف Workflow المعتمد

Workflow مسؤول عن **كل حدث أو إجراء فعلي يحدث بمرور الوقت ويغير سجل الحيوان أو البطن أو دورة الإنتاج أو موقع الإيواء أو المهمة التشغيلية**.

لا يقتصر على الدورة التناسلية.

القاعدة:

```text
Entity / Data
= من هو الحيوان؟ وما هو القفص؟

Workflow
= ماذا حدث للحيوان أو القفص أو البطن أو المهمة؟ ومتى؟ ولماذا؟ ومن نفذه؟
```

### الشجرة المستهدفة المعتمدة

```text
الحركات ودورة التشغيل الفعلية
├── استقبال الحيوان من الخارج وإعادة الإدخال
├── التسكين والنقل والإخلاء وإدارة الإشغال
├── الوزن والقياسات التشغيلية
├── التلقيح وإدارة المحاولات
├── فحص الحمل ومتابعة الحمل وتجهيز الولادة
├── تسجيل الولادة وإنشاء البطن
├── الرضاعة ومتابعة البطن وتداخل دورات الأم
├── الفطام والتحول إلى التتبع الفردي
├── النمو والفرز وإعادة التقييم
├── تحديد المصير والاستبعاد من المسار
├── الإحلال والاعتماد داخل القطيع الإنتاجي
├── التسمين والجاهزية للبيع
├── الصحة والعزل والتعافي والنفوق
├── الحالات الاستثنائية وإعادة بناء المسار
├── الخروج من المزرعة وإعادة الدخول
├── تشغيل وصيانة وتجهيز مواقع الإيواء
└── تنفيذ وإدارة المهام التشغيلية
```

### حالة الشجرة

**APPROVED** كأساس لخطة التنفيذ وإنشاء الأسئلة لاحقًا.

يمكن أثناء إعداد Implementation Plan تحسين أسماء Subsections أو دمج المتقارب منها إذا لم يتغير النطاق المعماري المعتمد، لكن لا يحذف نطاق وظيفي من القائمة دون مناقشة جديدة.

### قواعد فصل مهمة

#### الوزن

```text
تسجيل الوزن/القياس الفعلي → Workflow
قواعد وموعد ومستهدف الوزن → Settings
المنحنيات والتحليل → Reports / Analytics
```

#### المهام

```text
قواعد توليد المهمة وموعدها وأولويتها → Settings
تنفيذ/تأجيل/إلغاء/إغلاق المهمة وتسجيل نتيجتها → Workflow
عرض مهام اليوم والمتأخرات → Dashboard / Reports
```

#### الجاهزية

```text
قواعد الجاهزية → Settings
تنفيذ انتقال أو قرار فعلي → Workflow
عرض الجاهزية وأسباب عدمها → Reports / Dashboard
```

#### المواقع والإشغال

```text
تعريف Farm / Barn / Battery / Cage → Farm Structure
التسكين / النقل / الإخلاء / الصيانة / التطهير / العودة للخدمة → Workflow
قواعد السعة والإتاحة والتطهير → Settings
عرض الإشغال والسعة والحالات → Reports / Analytics
```

### حركات المواقع والمهام

تم اعتماد إبقاء حركات المواقع وLifecycle المهام التشغيلية داخل Workflow بدل إنشاء Main Sections مستقلة، لأن الاثنين يجيبان عن نفس السؤال المعماري:

> ما الذي حدث فعليًا؟

والتفاصيل والأسباب لكل Subsection موثقة في `QUESTIONNAIRE_SECTION_ARCHITECTURE_REVIEW.md`.

## 9. اتجاه القسم الخامس — التقارير والتحليلات والتنبيهات ومؤشرات الأداء — TO REVIEW

الاسم المستهدف:

`التقارير والتحليلات والتنبيهات ومؤشرات الأداء`

القسم الحالي متضخم ويحتاج إعادة تجميع قبل إنشاء أسئلته.

الاتجاه العام المتوقع أن يغطي:

- Dashboard ومؤشرات اليوم.
- تقارير القطيع.
- الخصوبة والتلقيح.
- الولادة والرضاعة والفطام.
- النمو والأوزان والتسمين.
- النفوق والصحة.
- تقييم الذكور والإناث.
- النسب والإحلال.
- الإشغال والسعة والمواقع.
- الاتجاهات والمقارنات.
- KPIs.
- الإنذار المبكر.
- جودة البيانات.
- التصفية والتصدير.

ملاحظات معمارية أولية:

- `مستويات التنبيه` يرجح أن تكون Settings لا Report مستقلًا.
- Lifecycle تنفيذ المهمة belongs to Workflow.
- قواعد توليد المهمة belong to Settings.
- عرض مهام اليوم belongs to Dashboard / Reports.
- `مبدأ التقرير → التنبيه → القرار → الإجراء` يرجح أن يكون مبدأ معماريًا لا Subsection مستقلًا.

التفاصيل النهائية ما زالت `TO REVIEW`.

## 10. اتجاه القسم السادس — الإعدادات وقواعد التشغيل


الاسم المستهدف:

`الإعدادات وقواعد التشغيل`

من الموضوعات المتوقعة بعد اكتمال المراجعة:

- نموذج Operational Settings Profile ونطاق تطبيقه.
- قواعد التلقيح والحمل والولادة.
- قواعد الفطام.
- قواعد النمو والفرز والإحلال.
- قواعد التسمين.
- قواعد الصحة والعزل.
- قواعد التسكين والسعة والتطهير.
- قواعد المهام والمواعيد.
- إعدادات التقارير وKPIs.
- حدود ومستويات التنبيهات.

هذه قائمة مراجعة وليست Requirements نهائية حتى يتم تصميم الأسئلة والإجابة عليها.

## 13. طريقة التشغيل الحالية أثناء إعادة البناء

المستخدم يعتمد حاليًا محليًا على:

```bash
php artisan migrate:refresh --seed
```

هذا الأمر **تدميري** ويعيد بناء قاعدة البيانات بالكامل.

تم اعتماده مؤقتًا لأن الإجابات القديمة تم الاستغناء عنها أثناء تنظيف الهيكل قبل بدء دورة إجابات جديدة.

كل Seed كامل يجب أن:

- ينشئ Main Sections بالترتيب المنفذ حاليًا.
- ينشئ Subsections في Parent الصحيح.
- يزرع كل الأسئلة المعتمدة.
- لا يعتمد على سجلات متبقية من تشغيل سابق.
- لا يخفي مجموعة أسئلة بسبب نسيان orchestrator.

## 14. الانتقال لاحقًا إلى الحفاظ على الإجابات

بمجرد بدء دورة إجابات نريد الاحتفاظ بها، لا يستخدم `migrate:refresh --seed` كطريقة تشغيل عادية على قاعدة البيانات التي تحتوي هذه الإجابات.

المبدأ:

```text
Stable Section Record
+ Stable section_id
+ Stable seed_key
+ Stable option value
+ preserveAnswers = true
```

هوية السؤال:

```text
section_id + seed_key
```

هوية Option:

```text
question_id + value
```

لا يتغير `seed_key` لمجرد تغيير صياغة السؤال إذا ظل القرار الوظيفي نفسه.

لا تتغير `option.value` لمجرد تعديل Label إذا ظل المعنى نفسه.

أي تغيير تدميري يجعل إجابة موجودة غير صالحة يجب أن يوقف المزامنة برسالة واضحة بدل حذف البيانات بصمت.

## 15. نقل الأقسام مع وجود إجابات

إذا احتجنا لاحقًا إلى إعادة تصنيف Subsection مع وجود إجابات:

المسموح:

```text
نفس Section Record
→ تعديل parent_id
→ الحفاظ على Section ID
```

غير المسموح:

```text
Delete subsection
→ Create subsection جديد
→ Recreate questions
```

لأن ذلك يعرض Question IDs والإجابات والعلاقات للخطر.

## 16. المرجع الوظيفي الأساسي للأسئلة

`تصور_مشروع_الارانب.md`

هو Source of Reference الوظيفي عند إنشاء أو مراجعة الأسئلة.

قبل إنشاء أسئلة جديدة يجب دائمًا:

1. مراجعة الجزء المقابل من الملف.
2. مراجعة الأقسام والأسئلة الحالية في المشروع.
3. مراجعة `QUESTIONNAIRE_SECTION_ARCHITECTURE_REVIEW.md` إذا كان القسم خضع لإعادة الهيكلة.
4. تجنب تكرار سؤال أو قرار تم تغطيته.
5. تحويل النقاط غير المحسومة إلى أسئلة تؤدي إلى قرارات واضحة.
6. الحفاظ على المصطلحات والمنطق الموجودين في المرجع.
7. عدم اختراع متطلبات غير مدعومة وكأنها حقائق.

إذا اعتمد المستخدم قرارًا أحدث، تكون الأولوية للقرار الأحدث داخل الـBlueprint دون تعديل `تصور_مشروع_الارانب.md` إلا بطلب صريح.

عند كتابة المتطلبات النهائية لا يرجع Requirements Agent إلى المرجع الوظيفي القديم ليغير قرارًا حُسم بالأسئلة والإجابات.

```text
Latest agreed decision
→ Approved Answer
→ Questionnaire Guide
→ Final Requirements Input
```

3. Final Requirements Input.
4. `docs/questionnaire-guide/REQUIREMENTS_CONFLICTS.md`

## 18. فلسفة إنشاء الأسئلة

كل سؤال يجب أن ينتج قرارًا قابلًا للتحويل إلى Requirement أو Rule مثل:

- Field.
- Required / Nullable Rule.
- Relationship.
- Workflow Rule.
- Validation.
- State / Status.
- Task / Alert.
- Audit / History Rule.
- Configuration Rule.

أي Requirement أساسي يجب أن يكون ممثلًا بسؤال صريح، حتى إذا كان اتجاه القرار معروفًا مسبقًا.

يمكن أن يكون السؤال:

- Discovery Question.
- Confirmation Question.

يحذف السؤال إذا كان لا ينتج قرارًا مفيدًا أو موجودًا في القسم الخطأ أو مكررًا، وليس لمجرد أن إجابته تبدو بديهية.

## 19. Question Types وDependencies

راجع دائمًا:

`App\Enums\Questionnaire\QuestionType`

الأنواع الحالية:

- `text`
- `textarea`
- `number`
- `date`
- `yes_no`
- `single_choice`
- `multi_choice`
- `select`

راجع أيضًا:

`App\Enums\Questionnaire\QuestionDependencyOperator`

الـEngine يدعم حاليًا:

- `EQUALS`
- `CONTAINS`

لا يتم افتراض Type أو Operator جديد قبل مراجعة الكود والحاجة الوظيفية واعتماده.

## 20. Question Seeder Sync

الخدمة الموحدة:

`app/Services/Questionnaire/QuestionSeederSyncService.php`

القواعد:

- لكل سؤال `seed_key` ثابت.
- تتم المزامنة بدل الحذف وإعادة الإنشاء العمياء.
- يتم ضبط `prune` و`preserveAnswers` وفق مرحلة العمل.
- عند الحفاظ على الإجابات، أي تغيير غير متوافق يجب أن يفشل بوضوح بدل فقد البيانات.

## 21. بيانات المزرعة — قرارات تأسيسية

`بيانات المزرعة` جزء من `هيكل المزرعة`.

الموقع الوظيفي يدعم:

- المحافظة.
- المدينة.
- العنوان.
- الموقع على الخريطة.

بيانات الاتصال يجب أن تدعم التعدد عند الحاجة، ولا يتم افتراض `phone_1`, `phone_2` كتصميم نهائي.

نشاط المزرعة لا يخزن كاختيار مستقل؛ الأنشطة الفعلية تستنتج من أنشطة العنابر التابعة لها.

## 22. الأنشطة التشغيلية

الأنشطة التشغيلية Master Data مستقلة.

الاتجاه الحالي:

> النشاط التشغيلي يرتبط بالعنبر وليس بالمزرعة.

أمثلة المرجع الوظيفي:

- إنتاج.
- فطام.
- تسمين.
- حجر / عزل.
- متعدد الاستخدام.

العلاقات في النظام النهائي تعتمد على IDs / Foreign Keys وليس الأكواد النصية.

## 23. المستخدمون وفريق التشغيل

المبادئ الحالية:

- عضو فريق التشغيل User لديه Login.

- يجب الحفاظ على السجل التاريخي عند تغير نطاق العمل أو الوردية.

التفاصيل النهائية تحسم بأسئلة صريحة.

## 24. المحافظات والمدن وقوائم الأسباب

المحافظات والمدن Master Data مستقلة:

```text
Governorate
    ↓ 1:N
City
```

قوائم الأسباب التالية Master Data مستقلة:

- أسباب الاستبعاد.
- أسباب الخروج.
- أسباب تغيير الذكر.

القيم التاريخية لا تحذف بطريقة تكسر السجلات السابقة؛ سياسة التعطيل/الحذف تحسم بالأسئلة المعتمدة.

## 25. تعدد اللغات

```text
name_ar
name_en
```

الأرقام والتواريخ والـIDs والقيم التقنية لا تحتاج ترجمة.

## 26. Questionnaire Guides

ملفات `docs/questionnaire-guide/` تشرح كيفية تفسير كل سؤال وإجابته لاحقًا.

وظيفتها:

- ربط السؤال بـ`seed_key`.
- شرح ما الذي ينتج من الإجابة.
- توضيح ما لا يجوز استنتاجه.
- منع إعادة تفسير القرار بصورة مختلفة في مرحلة Requirements.

لا يجب أن تصبح نسخة ثانية من الإجابات الفعلية.

بعد فصل Farm Structure، يتم لاحقًا إعادة تنظيم ملفات Guide التاريخية التي ما زالت تحت `questionnaire-guide/master-data/` بخطوة توثيقية مستقلة، ولا تنقل بصورة عمياء.

## 27. القفص / العين — الاتجاه الحالي

القفص جزء من `هيكل المزرعة`.

المبادئ الحالية:

```text
Battery Structure
→ Generate Cages
→ Cage gets fixed identity
→ Review / Activation
→ Operational Cage
→ every later change = Action + History Record
```

قواعد أساسية:

- لا Create مستقل للقفص.
- لا Delete مستقل للقفص.
- Cage Code فريد على مستوى النظام.
- QR Code يولد من هوية/كود القفص.
- بعد التفعيل تكون الهوية والموقع الهيكلي Immutable.
- تغييرات الحالة تتم عبر Actions وليس Edit Form.
- كل Action يسجل History / Audit.
- الإشغال الحالي ينتج من حركات التسكين والنقل.
- Cage Master Identity منفصلة عن Cage Operational State.

Seeder الحالي:

`database/seeders/Questions/FarmStructure/CageDataQuestionsSeeder.php`

### ملاحظة أثناء إعادة الهيكلة

الأسئلة الحالية التي ما زالت تحت الإجابة — مثل سؤال الأنواع الفيزيائية للبطاريات — يمكن تأجيلها حتى تثبيت الشجرة إذا كان مكانها أو تفسيرها قد يتأثر بإعادة التقسيم.

## 28. بيانات البطارية — قواعد مهمة

Battery جزء من Farm Structure ويتبع Barn واحدًا.

أهم الاتجاهات الحالية:

- Battery Code فريد على مستوى النظام.
- بنية البطارية تحدد الأقفاص التابعة لها.
- الأقفاص تولد بعد اكتمال البنية ومراجعتها.
- أي تاريخ تشغيلي على Cage يقفل الهوية الهيكلية التاريخية.
- لا يعاد استخدام هوية/كود Cage تاريخي.
- إعادة هيكلة Battery بعد وجود تاريخ تشغيلي تتطلب إنهاء الهيكل القديم وإنشاء هيكل جديد عند الحاجة.
- توقف/صيانة Battery يؤثر على الإتاحة التشغيلية للأقفاص دون تغيير حالاتهم المحلية تلقائيًا.

## 31. قاعدة تنفيذ إعادة الهيكلة الحالية

لا يتم تنفيذ تغييرات الأقسام 3–6 بصورة متفرقة أثناء النقاش.

المسار المعتمد:

```text
مناقشة وتوثيق
→ اعتماد الشجرة النهائية
→ استخراج Implementation Plan واضح
→ تنفيذ التعديلات على Section Seeders
→ إنشاء/إعادة تنظيم Question Seeder folders وOrchestrators
→ تحديث الوثائق
→ migrate:refresh --seed أثناء مرحلة التطوير الحالية
→ مراجعة النتيجة
→ بدء دورة الإجابات الجديدة
```

الهدف هو عدم العودة مرة أخرى إلى دوامة نقل الأقسام والأسئلة بعد بدء إجابات نريد الحفاظ عليها.

## 32. قاعدة GitHub الإلزامية

المستودع افتراضيًا:

**READ ONLY**

يسمح بالقراءة والبحث والتحليل والمراجعة والاقتراح فقط.

لا يتم تعديل أو إنشاء أو حذف ملف أو Commit أو Push أو Branch أو Pull Request أو Seeder إلا بطلب صريح ومباشر من المستخدم.

وجود صلاحية تقنية لا يعني وجود إذن بالتعديل.

`تصور_مشروع_الارانب.md` Reference Only ولا يتم تعديله إلا بطلب صريح.

بعد تعديل GitHub بطلب صريح، المسار المحلي المعتاد:

```bash
git pull origin master
```

وفي مرحلة إعادة البناء الحالية فقط:

```bash
php artisan migrate:refresh --seed
```
