# Farm Blueprint — Project Context & Working Rules

## 1. تعريف المشروع

المستودع الأساسي:

`hanyfreestyle/farm-blueprint.test`

هذا المشروع **ليس نظام إدارة مزرعة الأرانب النهائي**.

وظيفته بناء **Blueprint / دراسة تحليلية تفصيلية** قبل تطوير النظام الفعلي، وتحويل التصور ودورة العمل إلى:

**أقسام → أقسام فرعية → أسئلة → إجابات → قرارات ومتطلبات → تقارير فنية → Blueprint قابل للتنفيذ.**

الهدف من الأسئلة هو الوصول إلى **Software Requirements وBusiness Rules** موثقة، وليس جمع معلومات عامة فقط.

## 2. التقنية المستخدمة

- Laravel 12
- PHP 8.2
- Filament 4
- MySQL
- Questionnaire Engine مخصص
- `spatie/laravel-translatable` للبيانات متعددة اللغات عند الحاجة

## 3. الهيكل المنطقي للدراسة

الأقسام الرئيسية الحالية:

1. إدارة البيانات الأساسية — Master Data / Foundation.
2. إعدادات التشغيل — Operation Settings.
3. تكوين وإدخال القطيع — Herd Setup.
4. الحركات ودورة التشغيل — Workflow.
5. التقارير والإشعارات ومؤشرات الأداء — Reports.

القسم الأول يمثل الـFoundation الذي تعتمد عليه بقية أجزاء النظام.

## 6. بيانات المزرعة — قرارات تأسيسية

عند بناء أسئلة بيانات المزرعة يجب وجود سؤالين أساسيين على الأقل:

1. ما البيانات التي يجب أن يحتوي عليها ملف المزرعة؟
2. أي من هذه البيانات يجب أن يكون إلزاميًا؟

الهدف:

- السؤال الأول → Fields / Relationships المطلوبة.
- السؤال الثاني → Required / Nullable / Validation Rules.

### الموقع الجغرافي

الموقع المطلوب وظيفيًا يتكون من:

- المحافظة.
- المدينة.
- العنوان.
- الموقع على الخريطة.

### بيانات الاتصال

يجب دعم:

- أكثر من رقم هاتف.
- رقم واتساب أو أكثر عند الحاجة.

لا يتم افتراض أن التصميم النهائي سيكون `phone_1`, `phone_2`؛ المطلوب هو دعم التعدد وظيفيًا، ويمكن أن يتحول إلى Relationship مستقل.

### المالك والمسؤولون

لا يوجد احتياج حالي لتأسيس "مالك المزرعة" كحقل تشغيلي رئيسي.

المسؤولون عن التشغيل هم Users يمكنهم تسجيل الدخول إلى لوحة التحكم، ويتم التعامل معهم في قسم المستخدمين وفريق التشغيل.

---

## 7. الأنشطة التشغيلية

تم اعتماد الأنشطة كـMaster Data مستقلة:

- Module مستقل.
- Table مستقل في النظام النهائي.
- قابلة للإدارة من لوحة التحكم.
- الاسم `JSON / translatable` بالعربية والإنجليزية.
- الربط يعتمد على IDs وForeign Keys وليس الأكواد النصية.

الاتجاه التصميمي الحالي هو أن **النشاط التشغيلي يرتبط بالعنبر**، ويمكن استنتاج الأنشطة الفعلية للمزرعة من أنشطة العنابر التابعة لها.

أي أسئلة قديمة تربط النشاط مباشرة بالمزرعة تعتبر حاليًا ضمن مرحلة المراجعة ويمكن حذفها أو تعديلها بسهولة من خلال نظام Sync الجديد عند اعتماد القرار النهائي.

---

## 8. ملفات إعدادات التشغيل

تم إنشاء Subsection مستقل باسم:

`ملفات إعدادات التشغيل`

الاتجاه التصميمي الحالي:

```text
Operational Settings Profile
        ↓
      Barn
```

أي أن الإعدادات **ليست إعدادات على مستوى المزرعة**.

يمكن إنشاء أكثر من ملف إعدادات تشغيل، ويُستخدم ملف مناسب مع العنبر.

يجب أن تتحول القرارات الأساسية مثل:

- هل اختيار ملف إعدادات للعنبر إلزامي؟
- هل يمكن استخدام نفس ملف الإعدادات لأكثر من عنبر؟
- هل يمكن تغيير الملف بعد بدء التشغيل؟
- كيف نحافظ على تاريخ الإعدادات المستخدمة؟

إلى **أسئلة صريحة** في القسم المناسب حتى تظهر كRequirements في التقرير والـBlueprint النهائي.

## 9. المستخدمون وفريق التشغيل والورديات

هذا الجزء من الـFoundation لأنه يؤثر على التشغيل والمهام والتنبيهات والتدقيق.

المبادئ الحالية:

- عضو فريق التشغيل هو User لديه Login.
- يمكن ربط المستخدم بالمزرعة أو المزارع التي يعمل عليها.
- له Role / Permissions.
- يجب دعم Shifts / الورديات.
- ربط المستخدم بالمزرعة يساعد لاحقًا في تحديد نطاق الوصول لما يتبعها.
- يجب الانتباه للسجل التاريخي إذا تغيرت وردية المستخدم مستقبلًا.

التفاصيل النهائية تحسم بأسئلة صريحة.

## 10. المحافظات والمدن

المحافظات والمدن Master Data مستقلة وتم وضعها في آخر ترتيب قسم إدارة البيانات الأساسية.

## 11. قوائم الأسباب التشغيلية

القوائم التالية Master Data مستقلة:

- أسباب النقل.
- أسباب النفوق.
- أسباب الاستبعاد.
- أسباب الخروج.
- أسباب تغيير الذكر.

كل واحدة:

- Module مستقل.
- Table مستقل.
- قابلة للإدارة من لوحة التحكم.
- العلاقات تعتمد على IDs / Foreign Keys.
- لا تعتمد على `code` كهوية للعلاقة.

الحد الأدنى المقترح لاحقًا:

```text
id
name JSON / translatable
is_active
sort_order
created_at
updated_at
```

وجود `is_active` يسمح بإيقاف قيمة بدون حذفها وكسر السجل التاريخي.

## 12. قاعدة تعدد اللغات

النظام النهائي عربي / إنجليزي في لوحة التحكم والمخرجات التي تحتاج ترجمة.

أي اسم أو وصف إداري قابل للعرض باللغتين يستخدم **Translatable JSON** بدل:

```text
name_ar
name_en
```

النمط:

```json
{
    "ar": "الإسكندرية",
    "en": "Alexandria"
}
```

ينطبق على أمثلة مثل:

- الأنشطة التشغيلية.
- المحافظات.
- المدن.
- السلالات.
- أسباب النقل والنفوق والاستبعاد والخروج وتغيير الذكر.
- أي Master Data مشابه لاحقًا.

الأرقام والتواريخ والـIDs والإحداثيات والقيم التقنية لا تحتاج ترجمة.

## 13. قاعدة العلاقات والهوية في النظام النهائي

العلاقات بين كيانات النظام النهائي تعتمد على:

**IDs + Foreign Keys**

ولا تعتمد على الأكواد النصية.

أمثلة:

```text
cities.governorate_id
barn.activity_id حسب التصميم النهائي
barn.settings_profile_id حسب التصميم النهائي
mortality_record.mortality_reason_id
transfer_record.transfer_reason_id
exclusion_record.exclusion_reason_id
```

يمكن وجود Code لأغراض تشغيلية، لكنه ليس أساس الربط بين الجداول.

## 14. الملف المرجعي الوظيفي الأساسي

`تصور_مشروع_الارانب.md`

هو Source of Reference لدورة العمل ومتطلبات النظام.

عند إنشاء أو مراجعة أسئلة:

1. قراءة الجزء المقابل من الملف.
2. الحفاظ على المصطلحات والمنطق الموجود فيه.
3. مراجعة الأسئلة والقرارات الموجودة لمنع التكرار غير المقصود.
4. عدم اختراع متطلبات غير مدعومة وكأنها حقائق.
5. فصل أي بحث خارجي عن المرجع بوضوح.

الملف Reference Only ولا يتم تعديله إلا بطلب صريح.

## 15. فلسفة إنشاء الأسئلة — قاعدة محدثة

كل سؤال يجب أن ينتج قرارًا مفيدًا مثل:

- Field.
- Required / Nullable Rule.
- Relationship.
- Workflow Rule.
- Validation.
- State / Status.
- Task / Alert.
- Audit / History Rule.
- Configuration Rule.

### قاعدة إلزامية

**أي Requirement أساسي يجب أن يكون ممثلًا بسؤال صريح داخل الاستبيان، حتى إذا كانت الإجابة تبدو بديهية أو كان اتجاه القرار معروفًا مسبقًا.**

السبب أن الإجابة هي المرجع الرسمي الذي ستعتمد عليه التقارير والـBlueprint النهائي.

يمكن اعتبار الأسئلة نوعين:

1. Discovery Question — لاكتشاف قرار غير محسوم.
2. Confirmation Question — لتثبيت Requirement معروف الاتجاه داخل المخرجات الرسمية.

لا يحذف السؤال لمجرد أن إجابته بديهية؛ يحذف فقط إذا كان لا ينتج Requirement / Rule / Relationship / Field / Workflow Decision مفيد.

## 18. Question Seeder Sync — القاعدة الجديدة

تم اعتماد نظام موحد لمزامنة الأسئلة بدل كتابة منطق الحذف والتحديث داخل كل Seeder.

الخدمة:

`app/Services/Questionnaire/QuestionSeederSyncService.php`

### seed_key

أضيف حقل ثابت لكل سؤال:

`seed_key`

مثال:

```text
farm.fields
farm.required_fields
farm.code_strategy
farm.delete_policy
```

`seed_key` خاص بهوية السؤال داخل الـBlueprint / Seeders فقط، وليس Code للعلاقات في نظام المزرعة النهائي.

هوية السؤال أصبحت تعتمد على:

```text
section_id + seed_key
```

وليس:

```text
section_id + sort_order
```

وبالتالي يمكن تغيير ترتيب السؤال أو صياغته بدون تغيير هويته.

### Options

هوية Option داخل السؤال تستمر بالاعتماد على:

```text
question_id + value
```

ويتم استخدام `updateOrCreate` بدل الحذف وإعادة الإنشاء العمياء.

---

## 19. أوضاع المزامنة

`QuestionSeederSyncService` يدعم مفهومين مهمين:

### مرحلة التصميم الحالية

Seeders الحالية تستخدم:

```text
prune = true
preserveAnswers = false
```

المعنى:

- Seeder هو Source of Truth للقسم.
- السؤال المحذوف من تعريفات Seeder يحذف من قاعدة البيانات.
- Answer وOptions التابعة له تحذف تلقائيًا بسبب Cascade.
- إذا تغير نوع سؤال أو اختفت Option مستخدمة وأصبحت الإجابة غير صالحة، يمكن حذف الإجابة أثناء مرحلة التصميم.
- إعادة ترتيب الأسئلة لا تكسر الهوية لأن الربط أصبح بـ`seed_key`.

هذا الوضع **متعمد حاليًا لأننا ما زلنا نبني ونراجع الـBlueprint**.

### مرحلة الاستقرار لاحقًا

عند وجود إجابات يجب اعتبارها بيانات مرجعية مهمة، نستخدم:

```text
preserveAnswers = true
```

وعندها أي تغيير تدميري يجعل إجابة موجودة غير صالحة يوقف الـSync برسالة واضحة بدل حذف البيانات.

---

## 20. Cascade الحالي

قاعدة البيانات الحالية تحتوي على:

```text
questionnaire_answers.question_id → cascadeOnDelete
questionnaire_question_options.question_id → cascadeOnDelete
```

لذلك حذف سؤال ملغي من Sync Service يؤدي تلقائيًا إلى حذف إجابته وخياراته بدون منطق حذف مكرر داخل كل Seeder.

---

## 21. شكل Question Seeder الجديد

كل Seeder يجب أن يكون في الأساس مجرد تعريف للأسئلة:

```php
$questions = [
    [
        'seed_key' => 'farm.fields',
        'title' => '...',
        'type' => QuestionType::MULTI_CHOICE,
        'sort_order' => 1,
        'options' => [...],
    ],
];

app(QuestionSeederSyncService::class)->sync(
    mainSectionName: 'إدارة البيانات الأساسية',
    sectionName: 'بيانات المزرعة',
    questions: $questions,
    prune: true,
    preserveAnswers: false,
);
```

لا يكرر كل Seeder منطق البحث والحذف ومقارنة الإجابات ومزامنة Options.

## 23. إعادة بناء قاعدة البيانات أثناء مرحلة التطوير

الأوامر التالية **تدميرية** وتحذف البيانات الحالية، وتستخدم فقط عندما يكون المقصود إعادة بناء بيئة التطوير من الصفر:

```bash
php artisan migrate:fresh --seed
```

أو:

```bash
php artisan migrate:refresh --seed
```

في هذه المرحلة، عند الرغبة في Reset كامل ونظيف، يفضل عادة:

```bash
php artisan migrate:fresh --seed
```

لأنه يسقط الجداول ويعيد إنشاءها مباشرة بدل الاعتماد على `down()` لكل Migration.

لا يستخدم أي من الأمرين على قاعدة بيانات تحتوي على إجابات نريد الاحتفاظ بها.

## 26. قواعد GitHub الإلزامية

المستودع يتم التعامل معه افتراضيًا كـ:

**READ ONLY**

يسمح بالقراءة والبحث والتحليل والمراجعة والاقتراح فقط.

لا يتم تعديل أو إنشاء أو حذف ملف، ولا Commit أو Push أو Branch أو Pull Request أو Seeder، إلا بطلب صريح ومباشر من المستخدم.

**وجود صلاحية تقنية لا يعني وجود إذن بالتعديل.**

`تصور_مشروع_الارانب.md` Reference Only ولا يتم تعديله إلا بطلب صريح.
