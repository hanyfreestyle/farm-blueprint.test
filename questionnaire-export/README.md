# Questionnaire Export — خطة العمل

## 1. الهدف

هذا المجلد مخصص لتنظيم مخرجات دراسة الـQuestionnaire قبل الانتقال إلى كتابة الـRequirements التنفيذية.

الفكرة الأساسية هي الفصل الصريح بين مصدرين مختلفين:

```text
Answers Export
= ماذا سألنا؟ وما الإجابة المعتمدة؟

Guides
= ماذا تعني هذه الإجابة تقنيًا؟ وما حدود تفسيرها؟
```

التصدير الآلي من النظام مسؤول عن **ملفات الإجابات فقط**.

أما ملفات الشرح والتفسير التقني فلا يتم توليدها تلقائيًا من الكود، بل يتم إنشاؤها لاحقًا بعد مراجعة كل قسم وتحليل إجاباته واعتماد التفسير.

---

## 2. البنية المستهدفة

```text
questionnaire-export/
│
├── README.md
├── INDEX.md
│
├── answers/
│   ├── 01-master-data/
│   ├── 02-farm-structure/
│   ├── 03-animal-herd/
│   ├── 04-workflow/
│   ├── 05-reports/
│   └── 06-settings/
│
└── guides/
    ├── 01-master-data/
    ├── 02-farm-structure/
    ├── 03-animal-herd/
    ├── 04-workflow/
    ├── 05-reports/
    └── 06-settings/
```

يجب أن تتطابق أسماء الملفات وترقيمها بين شجرة `answers` وشجرة `guides` بحيث يكون لكل ملف إجابات ملف شرح مقابل له عند اكتمال التفسير.

مثال:

```text
answers/01-master-data/01-operational-activities.md

guides/01-master-data/01-operational-activities.md
```

---

## 3. ملف INDEX.md

`INDEX.md` هو ملف الشجرة الرئيسي ولوحة متابعة حالة التصدير والشرح.

يعرض جميع الأقسام الرئيسية والأقسام الفرعية حتى لو لم يتم تصدير ملف الإجابات أو إنشاء ملف الشرح بعد.

لكل قسم فرعي يجب أن تظهر على الأقل البيانات التالية:

- رقم القسم.
- اسم القسم الفرعي.
- مسار ملف الإجابات المتوقع.
- حالة تصدير ملف الإجابات.
- مسار ملف الشرح المتوقع.
- حالة إنشاء ملف الشرح.

مثال:

```md
| # | القسم الفرعي | ملف الإجابات | حالة التصدير | ملف الشرح | حالة الشرح |
|---|---|---|---|---|---|
| 1.1 | الأنشطة التشغيلية | `answers/01-master-data/01-operational-activities.md` | ✅ تم التصدير | `guides/01-master-data/01-operational-activities.md` | ❌ لم يتم الإنشاء |
| 1.2 | الأغراض الإنتاجية | `answers/01-master-data/02-production-purposes.md` | ❌ لم يتم التصدير | `guides/01-master-data/02-production-purposes.md` | ❌ لم يتم الإنشاء |
```

### قاعدة الحالة

حالة ملف الشرح لا يتم تسجيلها يدويًا في قاعدة البيانات.

```text
إذا كان ملف Guide المقابل موجودًا فعليًا
→ ✅ تم الإنشاء

إذا لم يكن موجودًا
→ ❌ لم يتم الإنشاء
```

وبنفس المنطق، يعتبر ملف الإجابات "تم تصديره" عندما يكون ملف التصدير الخاص بالقسم موجودًا ضمن شجرة `answers` للناتج الحالي.

---

## 4. شجرة Answers

شجرة `answers` يتم توليدها من بيانات الـQuestionnaire الفعلية.

لكل قسم فرعي ملف Markdown مستقل.

الملف يمثل **مصدر الحقيقة للإجابة** ولا يحتوي على تفسير تقني مستنتج.

يجب أن يحتوي عند الحاجة على:

- اسم القسم الرئيسي.
- اسم القسم الفرعي.
- `Question Key / seed_key`.
- نص السؤال.
- `help_text`.
- نوع السؤال.
- الاختيارات وقيمها عند وجودها.
- هل السؤال مطلوب.
- `report_category`.
- `target_entity`.
- Dependency كاملة عند وجودها.
- الإجابة الحالية.
- ملاحظات المختص.
- حالة المراجعة.
- حالة قابلية السؤال الحالية إذا كان مشروطًا.

### الأسئلة غير المجاب عنها

لا يتم حذف السؤال غير المجاب عنه من ملف القسم.

يظهر بوضوح مثل:

```text
الإجابة الحالية: غير مجاب
```

الهدف أن يمثل التصدير الدراسة كاملة وليس القرارات المحسومة فقط.

### Dependencies

يجب تصدير Dependency بصورة واضحة بما يكفي لفهم منطق ظهور السؤال، وتشمل عند وجودها:

```text
Parent Question Key
Operator
Dependency Value
```

---

## 5. شجرة Guides

شجرة `guides` ليست جزءًا من التوليد الآلي لتفسير الإجابات.

مسار العمل الصحيح:

```text
Answer File
↓
مراجعة الإجابات
↓
تحليل المعنى التقني
↓
مناقشة واعتماد التفسير
↓
إنشاء Guide File المقابل
```

ملف الشرح يجيب عن أسئلة من نوع:

- ماذا تعني الإجابة تقنيًا؟
- ما القرار التصميمي الناتج عنها؟
- ما الحقول أو العلاقات أو القواعد التي يمكن أن تنتج عنها؟
- ما حدود الاستنتاج؟
- ما الذي لا يجوز افتراضه من الإجابة؟
- ما علاقتها بـQuestion Keys أو أقسام أخرى؟
- هل يوجد تعارض أو نقطة تحتاج قرارًا إضافيًا؟

الـGuide لا يكون مصدرًا بديلًا للإجابة الفعلية، بل طبقة تفسير لها.

---

## 6. الفصل بين الإجابة والتفسير

قاعدة ثابتة:

```text
Answers
= What did we decide?

Guides
= What does that decision mean technically?
```

لا يتم دمج الطبقتين في ملف واحد، ولا يقوم الـExporter باختراع تفسير تقني للإجابة.

---

## 7. تسلسل العمل المتفق عليه

يتم تنفيذ العمل على مراحل مستقلة:

### المرحلة 1 — بناء الشجرة

إنشاء `INDEX.md` يحتوي جميع الأقسام الرئيسية والفرعية وحالة كل من:

```text
Answer Export
Guide Creation
```

### المرحلة 2 — تصدير الإجابات

بعد الإجابة على قسم فرعي، يتم توليد ملفه داخل `answers/` ثم تحديث حالة التصدير في `INDEX.md`.

مثال البداية الحالية:

```text
1. إدارة البيانات الأساسية
└── 1.1 الأنشطة التشغيلية
    ├── الإجابات: ❌ لم يتم التصدير
    └── الشرح:    ❌ لم يتم الإنشاء
```

بعد الإجابة والتصدير:

```text
1. إدارة البيانات الأساسية
└── 1.1 الأنشطة التشغيلية
    ├── الإجابات: ✅ تم التصدير
    └── الشرح:    ❌ لم يتم الإنشاء
```

### المرحلة 3 — مراجعة الإجابات

يتم قراءة ملف الإجابات المصدر للقسم ومراجعته قبل كتابة أي تفسير تقني.

### المرحلة 4 — إنشاء ملف الشرح

بعد التحليل والمناقشة والاعتماد يتم إنشاء الملف المقابل داخل `guides/`.

تصبح الحالة:

```text
1. إدارة البيانات الأساسية
└── 1.1 الأنشطة التشغيلية
    ├── الإجابات: ✅ تم التصدير
    └── الشرح:    ✅ تم الإنشاء
```

### المرحلة 5 — الانتقال للقسم التالي

يتم تكرار نفس الدورة قسمًا فرعيًا بعد قسم حتى اكتمال الشجرتين.

---

## 8. الهدف النهائي من الشجرتين

بعد اكتمال العمل يصبح لدينا:

```text
Answers Tree
+
Guides Tree
↓
Requirements Input
↓
Final Requirements
```

شجرة الإجابات تحفظ القرارات الفعلية، وشجرة الشرح توضح معناها التقني وحدودها، وبذلك يمكن لاحقًا كتابة Requirements أكثر دقة دون الاعتماد على ملف Markdown ضخم أو إعادة تفسير المشروع من الصفر.

---

## 9. قواعد مهمة

1. لا يتم اختراع إجابة أثناء التصدير.
2. لا يتم اختراع تفسير تقني آليًا.
3. لا يتم حذف الأسئلة غير المجاب عنها من ملف القسم.
4. الربط الأساسي بين السؤال والتفسير يعتمد على `Question Key / seed_key` الثابت.
5. يفضل أن يتطابق اسم الملف المقابل داخل `answers` و`guides`.
6. `INDEX.md` يمثل حالة الشجرة الحالية ويجب أن يعكس الواقع الفعلي للملفات.
7. ملفات الشرح يتم إنشاؤها فقط بعد مراجعة وتحليل واعتماد التفسير.
8. تصدير الإجابات لا يعدل الإجابات الأصلية في قاعدة البيانات.
9. هذه البنية مستقلة عن التقرير الفني الحالي و`Final Requirements Input` الحالي، ويمكن استخدامها لاحقًا كمصدر منظم للمرحلة التالية.
